# Database model

## Ownership and identity

Better Auth owns users, accounts, sessions, verification records, organizations,
members, and invitations. Its organization plugin is enabled on the server and
client. `src/db/auth-schema.ts` is generated; domain tables live separately in
`src/db/domain-schema.ts`. `src/db/schema.ts` exports both for Drizzle. Keep
schema-affecting Better Auth options in `src/lib/auth-schema-options.ts`, shared
by runtime authentication and the generator configuration.

Auth IDs retain their text type and existing generation behavior. Domain IDs
are UUID strings generated by Drizzle on insert, stored as text so references
use one consistent type. Raw SQL inserts must supply domain IDs. Timestamps
follow the existing timestamp-without-time-zone convention; application values
are UTC. `updatedAt` uses Drizzle's application-side update hook, not a database
trigger.

Functional groups are named organization-owned collections of Better Auth users.
They do not confer permissions. Better Auth `member` is the sole source of
organization membership. Review responsibilities are strings on reviews, not
department columns or group roles. A review may have multiple individual/group
assignments; each assignment targets exactly one kind. Withdrawing an assignment
retains its record and permits reassignment. Project access rules and configurable
authorization policies are intentionally deferred.

## Tenancy and authorization

All domain records have an explicit organization foreign key. Composite foreign
keys include organization and, where necessary, proposal, project, and revision.
They prevent attaching a review, comment, approval, suggestion, decision source,
or delivery child to a different context, even if an ID is otherwise valid.
Nullable provenance is constrained so a missing parent cannot bypass the
corresponding composite foreign key.

These constraints ensure referential isolation; they do not authorize reads or
writes. No PostgreSQL row-level security or domain API is introduced here. Future
server queries must scope by an organization validated against the authenticated
Better Auth member, before fetching data. User references preserve attribution,
not proof of current membership. The server must validate current membership and
responsibility when assigning groups/reviews or performing domain actions. Group
membership and old assignments must never grant access after organization
membership has been removed. Historical actor references deliberately survive
removal of a Better Auth membership.

## Specification history

A proposal can start with only a title and no revision. Its problem statement and
lifecycle status are mutable working metadata. The reviewed artifact is a
specification revision, containing a title and the full Markdown specification
(including any approved problem statement and acceptance criteria). Each revision
has an author, creation time, positive number, and unique proposal-local ordering.
The highest number is the latest snapshot; no redundant current-revision pointer
needs synchronization. Revision numbers must be allocated transactionally; the
unique constraint rejects concurrent duplicates.

Revisions are append-only by contract: an edit or restore inserts a new snapshot.
There is no update timestamp or mutable document stored in place of history.
This schema does **not** install an UPDATE/DELETE prevention trigger or database
role grants. SQL issued with the migration owner's privileges can still change
snapshots. Before exposing revision writes, the server must implement append-only
writes and restrict the runtime database role accordingly; database-level write
protection needs a deliberate migration when deployment roles are defined.

Each review targets one revision and one named responsibility. Approvals target
that exact review/revision pair; the review supplies their responsibility. An
approval cannot be moved to another revision simply by changing its revision ID.
Revocation/staleness records an end time and reason. A subsequent grant is a new
record; only one grant per reviewer/review can be active. New revisions do not
inherit approvals, and no automatic approval invalidation workflow runs yet.
Readiness calculations must compare the reviewed revision to the current one and
apply materiality policy when that workflow is implemented. Proposal status is a
summary, never authorization or proof of readiness.

Threads always retain their originating revision and can optionally belong to a
review on that revision. Messages are separate records. Optional JSON anchors
leave room for editor-specific ranges and quoted text without choosing an editor
now. Resolution/reopening changes thread state without deleting messages; this
initial model does not retain a separate audit event for every state transition.

Suggestions contain replacement Markdown, an optional anchor, and optional thread
context. A null anchor means whole-document replacement. An accepted suggestion
must record the resolving user/time and a different resulting revision of the
same proposal. Future acceptance must transactionally create a **later** snapshot
and resolve the suggestion, validating the base content and handling concurrent
changes; foreign keys alone cannot establish ordering or text correctness.
Rejected suggestions retain their proposed text and resolution. No acceptance
service is implemented.

Readiness checks are revision-scoped evaluations with a key, evaluator identity,
status, blocking flag, and explanation/metadata. Each rerun inserts a result;
previous evidence is retained. Checks affected by mutable discussion/review state
must be reevaluated by future workflows even when the revision does not change.
There is no generic workflow engine or preconfigured readiness policy.

## Decisions and delivery

Decisions belong to a project, with optional proposal/revision/thread provenance.
They can be archived without erasing the source discussion. Editable decisions
are not themselves versioned in this initial model.

Delivery items are provider-neutral drafts tied to a source revision, with free
text category, Markdown description, order, and a parent in the same revision.
The database rejects self-parenting and cross-context parents; future hierarchy
writes must also reject longer cycles. Delivery-plan versioning and approval are
not implemented, so these records alone cannot authorize publication.

External identifiers, URLs, remote namespace, synchronization state, and metadata
live in a separate link table. The namespace identifies a provider installation
or workspace; provider-specific project/issue mappings belong in its metadata or
a future integration configuration. External identity is unique within an
organization/provider/namespace, and a draft can reserve a pending link before it
has an external ID. The link ID can serve as a stable operation identity, but the
schema alone does not implement publication idempotency or partial-failure
recovery. There are no credentials, network calls, or implicit bidirectional sync.
Local draft content is owned here; external identity and sync outcomes are owned
by the future adapter. Conflict resolution must precede any sync implementation.

## Retention

Domain history and actor references use restrictive foreign keys. Deleting a
project/proposal/organization with referenced history, or a referenced author,
fails instead of silently cascading. Archive timestamps on projects, proposals,
groups, decisions, and delivery items support reversible removal from active
views. Better Auth's original auth-table cascades are preserved, but domain
references intentionally prevent its hard-delete user/organization flows where
history exists. A future account erasure/anonymization policy and actionable error
handling must account for this. Removing an organization membership remains
possible and does not delete reviews or approvals. Only functional group
membership rows cascade with their parent group/user.

## Generation and verification

```bash
bun run auth:generate # only when Better Auth schema options change
bun run db:generate   # generate SQL and snapshot from the combined schema
bun run db:test       # apply and test migrations in a disposable PostgreSQL database
bun run check
```

The auth generator is version-pinned to the installed Better Auth version; update
them together. It needs no database connection or Next.js runtime imports. The
initial auth indexes are regenerated with the current CLI's names; their columns
and behavior are unchanged. Drizzle generates the migration SQL; do not hand-edit
it. Format changed generated JSON with Prettier when needed for `format:check`.

`db:test` connects to local Compose PostgreSQL by default, creates a randomly named
test database, and removes it afterward. Set `SCHEMA_TEST_DATABASE_URL` to a test
server account with CREATE DATABASE permission if needed. It deliberately ignores
`DATABASE_URL`. The tests upgrade an auth-only database with existing records,
reapply migrations, exercise Better Auth organization creation, and verify domain
constraints. They do not modify the application database.

Policies, project membership, integration configuration, AI, notifications,
realtime events, complete audit logging, editor-specific anchors, and application
workflow services are deferred until concrete behavior requires them.
