# Database model

## Ownership and identity

Better Auth owns users, accounts, sessions, verification records, organizations,
members, and invitations. Its organization plugin is enabled on the server and
client. `packages/core/src/db/auth-schema.ts` is generated; domain tables live separately in
`packages/core/src/db/domain-schema.ts`. `packages/core/src/db/schema.ts` exports both for Drizzle. Keep
schema-affecting Better Auth options in `packages/core/src/lib/auth-schema-options.ts`, shared
by runtime authentication and the generator configuration.

Auth IDs retain their text type and existing generation behavior. Domain IDs
are UUID strings generated by Drizzle on insert, stored as text so references
use one consistent type. Raw SQL inserts must supply domain IDs. Timestamps
follow the existing timestamp-without-time-zone convention; application values
are UTC. `updatedAt` uses Drizzle's application-side update hook, not a database
trigger.

Better Auth `member` is the sole source of organization membership and of the
fixed application role. `project_member` records who works in a project and
whether they administer it. Disciplines (`discipline`, per project) are named
groups of project members carrying work item capability flags; see
[organizations, projects and teams](organization-model.md). Review
responsibilities are strings on reviews (the requested discipline's name at
request time), not foreign keys. A review may have multiple individual or
discipline assignments; each assignment targets exactly one kind. Withdrawing
an assignment retains its record and permits reassignment. Active discipline
names are unique per project case-insensitively; archived disciplines keep
their rows so history stays legible. Private projects are intentionally
deferred.

## Tenancy and authorization

All domain records have an explicit organization foreign key. Composite foreign
keys include organization and, where necessary, work item, project, and revision.
They prevent attaching a review, comment, approval, suggestion, decision source,
or delivery child to a different context, even if an ID is otherwise valid.
Nullable provenance is constrained so a missing parent cannot bypass the
corresponding composite foreign key.

These constraints ensure referential isolation; they do not authorize reads or
writes. Domain services validate the authenticated person's current membership
and project discipline capabilities inside transactions before reading or
changing organization-owned data. The browser, MCP and embedded agent use those
same services. Historical actor and review references preserve attribution;
they do not grant access after membership is removed. PostgreSQL row-level
security is not the application's authorization mechanism.

## Specification history

A work item type determines whether the item carries a specification. Refinement
state and delivery status are separate. The reviewed artifact is an immutable
revision containing the title and full Markdown, with an author, creation time
and item-local revision number. Domain writes allocate numbers transactionally
and the unique constraint rejects duplicates.

Edits and restores insert snapshots rather than updating historical content.
Once readiness has passed, main stays protected and later proposals use branches
and reviewed pull requests. Commits preserve immutable snapshots and parent
relationships; branches point to commits. See
[revision and branch semantics](synchronization.md#revisions-reviews-and-conflicts).

Immutability of specification snapshots is a domain write invariant, not an
UPDATE/DELETE prevention trigger. Runtime roles have DML access; operators must
not treat direct SQL as a supported way to edit historical content. Production
role boundaries are described in [deployment](../operations/deployment.md#database-roles).

Reviews and approvals reference the exact work item and revision through
composite keys. Material main revisions stale earlier approvals and request
active reviews again; earlier decisions remain in history. Pull request reviews
bind to the complete proposed merge result. A different result needs review.

Threads retain their originating revision, quoted text or editor anchor, and
optional review or pull request context. Resolution and reopening preserve
messages and record activity. Decisions can retain the source discussion.

Legacy suggestions and their versioned decisions remain readable for historical
records. New proposals use branches and pull requests; merging creates a new
main revision. Child work proposed in a commit is applied atomically only when
the pull request merges.

Readiness is evaluated from current evidence: text, sections, blocking threads,
reviews, discipline approvals, sign-offs, child readiness and optional AI checks.
A project's Definition of Ready is versioned separately from the specification;
items pin the applicable policy version according to the
[delivery model](delivery.md#definition-of-ready). A ready label is a summary of
these facts, never independent authority to start or publish work.

## Decisions and delivery

Decisions belong to a project, with optional proposal/revision/thread provenance.
They can be archived without erasing the source discussion. Archiving and
restoring are project capabilities: specification editors curate every decision,
and an author may curate their own only while a discipline still lets them
record decisions (edit specifications or review). Authorship adds to a current
capability and never replaces it. Decision edits preserve their activity history; the decision text is not a
separate specification revision chain.

Delivery work is ordinary work items (see [delivery.md](delivery.md)); there is
no separate delivery-item table. Composite foreign keys keep a work item's
team, status and iteration inside its own project
(`organization_id, project_id, …`), and keep teams, types, statuses,
iterations, relations and iteration events inside one organization. One active
iteration per project is a partial unique index; iteration state and its
timestamps are constrained together.

A `delivery_connection` is an organization's authenticated access to one
external installation (a Jira Cloud site). Its base URL is the namespace and
never changes; the credential is AES-GCM encrypted with the organization id as
associated data and never leaves the server. A `delivery_target` maps one
project to an external project and its work item types to external types.

`work_item_external_link` records where an item was exported: at most one link
per item and connection, and an external identity maps to at most one local
item, so a retried export cannot create duplicate delivery work. A pending link
can be reserved before it has an external ID. The link remembers the revision
and payload hash last pushed and the external last-modified time right after
that push, so re-exports skip unchanged items and detect external edits.
Title, content and labels are owned here and pushed one-way on explicit export;
external status is a read-only copy. Adapters live behind
`src/delivery/provider.ts`; nothing else may know provider-specific shapes.

## Retention

Domain history and actor references use restrictive foreign keys. Deleting a
project/work item/organization with referenced history, or a referenced author,
fails instead of silently cascading. Deleting an organization is therefore an
explicit job that removes its rows table by table, in a checked order
([organization deletion](./organization-deletion.md)). Archive timestamps on projects, work items,
disciplines, teams, types, statuses, and decisions support reversible removal
from active views. Better Auth's original auth-table cascades are preserved, but domain
references intentionally prevent its hard-delete user/organization flows where
history exists, and its organization delete endpoint is disabled. Accounts are therefore never removed: deleting one anonymizes
the row and keeps it ([account deletion](./account-deletion.md)). Removing an
organization membership remains possible and does not delete reviews or
approvals. Only project, discipline and
team membership rows cascade with their parent rows.

## Generation and verification

```bash
bun run auth:generate # only when Better Auth schema options change
bun run db:generate   # generate SQL and snapshot from the combined schema
bun run db:test       # apply and test migrations in a disposable PostgreSQL database
bun run check
```

The auth generator is version-pinned to the installed Better Auth version; update
them together. It needs no database connection or application runtime imports. The
initial auth indexes are regenerated with the current CLI's names; their columns
and behavior are unchanged. Drizzle generates the migration SQL; do not hand-edit
it. Format changed generated JSON with Prettier when needed for `format:check`.

`db:test` connects to local Compose PostgreSQL by default, creates a randomly named
test database, and removes it afterward. Set `SCHEMA_TEST_DATABASE_URL` to a test
server account with CREATE DATABASE permission if needed. It deliberately ignores
`DATABASE_URL`. The tests upgrade an auth-only database with existing records,
reapply migrations, exercise Better Auth organization creation, and verify domain
constraints. They do not modify the application database.
