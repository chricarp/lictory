# Code hosts

The Code module connects an organization to GitHub, GitLab and Bitbucket and
puts their repositories, branches, pull requests, checks and issues next to
the work they deliver. It is the "Code" row of
[the software factory](software-factory.md#code). Code lives in
`packages/core/src/code`; the capabilities are in
`packages/core/src/capabilities/code.ts`.

## Ownership

- **The code host owns every mirrored field.** Repositories, branches, pull
  requests (title, state, review decision, head), checks, issues and commits
  are written only by ingest (webhooks, reconciliation, backfill) and by the
  outbox recording what a host answered. No command edits a mirror; a person
  or agent who wants a change asks the host for it through a write.
- **Lictory owns links.** A branch, pull request, issue or commit is linked to
  a work item because it names the item's key, because a person or agent
  linked it, because an agent session produced it, because the item was
  imported from the issue, or because Lictory created it for the item. Links
  are history: unlinking records who did it and when.
- **Mirrors only move forward.** A pull request or issue is never overwritten
  with data older than what is stored (`host_updated_at`), so a replayed or
  late delivery cannot roll state back.
- **An imported issue's work item is Lictory's.** Importing creates an
  ordinary work item through `createWorkItem`; the issue stays mirrored and
  linked, and its later changes do not touch the item.

## Hosts and credentials

| Host                                   | Connect with                                                                                                 | Credential agent sessions receive                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| GitHub (github.com, Enterprise Server) | A GitHub App installation (app id, private key, installation id), or a fine-grained personal access token    | App: an installation token for one repository, expiring within an hour |
| GitLab (gitlab.com, self-managed)      | A personal, group or project access token (`api`; `read_api` for a read-only mirror)                         | The stored token, flagged long-lived                                   |
| Bitbucket Cloud                        | A repository, project or workspace access token; an Atlassian API token with its email; or an OAuth consumer | OAuth consumer: a token expiring within two hours; otherwise the token |

Credentials are entered by an organization administrator in the browser only
(`connectCodeHost` is web-only, `humanOnly: credentials`), verified against
the host outside any transaction, encrypted with the delivery credentials key
(`delivery/credentials.ts`, organization id bound as associated data) and never
returned. The same rule as Jira applies in production without
`DELIVERY_CREDENTIALS_KEY`. Each connection has its own webhook secret,
generated by Lictory, encrypted the same way and shown once (on connect and
on rotation).

A stored token is long-lived and may reach more than the session's
repository. The connection's projection says so (`longLivedCredential`) and
settings warn; prefer a GitHub App or a Bitbucket OAuth consumer where
sessions run.

Bitbucket Data Center has a different API and follows as its own adapter
(`bitbucket_server`); nothing outside `code/bitbucket` knows Bitbucket Cloud's
shapes.

## The port

`CodeHostProvider` (`code/provider.ts`) is the boundary. The domain speaks in
`CodeRepositoryInfo`, `CodeBranchInfo`, `CodePullRequestInfo`,
`CodeChecksSummary`, `CodeIssueInfo`, `CodeCommitInfo` and `CodeWebhookEvent`;
each adapter (`code/github`, `code/gitlab`, `code/bitbucket`) translates its
REST payloads and webhook bodies. Reads: repositories, branches, pull requests
(with review decision and approvals), files changed, checks for a commit,
issues and commits. Webhooks: `verifyWebhook` and `parseWebhook`. Writes:
create a branch, find the open pull request for a head branch, open one,
find and post a comment, request a review, merge for an expected head, close
or reopen, and `createSessionCredential`.

Review decisions are computed from each person's latest deciding review
(GitHub's REST API does not report branch protection's decision; GitLab adds
its approval rules and reviewer states). When a host does not say which
checks are required, every reported check counts.

## Egress

Self-managed hosts are addresses administrators type, so every request goes
through `code/egress.ts`: https only, no credentials in the URL, redirects
never followed, cloud metadata and link-local addresses always refused (the
same rule as AI endpoints, `isMetadataAddress`), and private, loopback and
internal-suffix hosts refused unless the operator lists them in
`CODE_HOST_PRIVATE_HOSTS`. The check runs on the URL and again on the
addresses the name resolves to at connection time, so DNS rebinding is caught
too. Pagination only follows links to the API's own origin: the credential
goes with each request. Agent event webhooks use a different guard
(`lib/egress.ts`) for destinations anyone types; see
[agent events](agent-events.md#egress) for why the two are separate.

## Ingest

```text
host ──POST /api/code/webhooks/:connection──▶ verify signature ─▶ code_webhook_delivery (once per delivery id) ─▶ 202
                                                                         │ pg_notify('code')
worker ── claim under lease ─▶ parseWebhook ─▶ read again from the host ─▶ one transaction: mirrors, key links, projections
```

- **Verification.** GitHub `X-Hub-Signature-256` and Bitbucket
  `X-Hub-Signature` are HMAC SHA-256 of the exact body; GitLab
  `X-Gitlab-Token` is compared to the secret in constant time. The route
  verifies before it parses, needs no cookie (it is exempt from the
  same-origin rule) and answers the same way for an unknown connection and a
  bad signature.
- **Dedupe.** Deliveries are unique per connection and delivery id
  (`X-GitHub-Delivery`, `X-Gitlab-Event-UUID`, `X-Request-UUID`; GitLab
  versions without an event UUID use the body's digest). A replay is a
  duplicate and changes nothing.
- **Events are hints.** Pull requests, issues and checks are read again from
  the host before anything is written, so a missed, duplicated or reordered
  delivery never leaves a wrong aggregate. Pushes are used as delivered (the
  commits they name).
- **Leases.** A delivery is claimed with `lease_until` and its attempt count,
  which also fences the result: a worker whose lease expired writes nothing.
  Failures retry with backoff and give up after six attempts; the
  reconciliation repairs what they would have changed. Settled deliveries are
  pruned after fourteen days.
- **Reconciliation and backfill.** Every repository a project uses is read
  again every ten minutes (`sync_due_at`): pull requests and issues updated
  since the last run (with a margin), open pull requests' reviews and checks,
  branches that name a key (and branches the host deleted), and key-naming
  commits on the default branch. Linking a repository makes it due at once,
  which backfills the last thirty days.

**Text is data.** A payload can name a work item (key detection) but never
authorizes anything.

## Key detection

A key is a project key, a hyphen and a number (`PAY-142`), matched
case-insensitively and only as a whole word: `xpay-142`, `PAY-142a` and
`PAY_142` do not name PAY-142, and `PAY-1423` names 1423. Branch names, pull
request titles and descriptions, issue titles and descriptions and commit
messages are searched, and **only for the projects the repository is linked
to**. A pull request's head branch is linked to whatever the pull request is
linked to.

Detection never recreates a link a person removed: unlinking is a decision
later mentions do not overrule. A person can still link it again on purpose.

## Writes

Writes (create a branch, open, comment on, request a review of, merge, close
or reopen a pull request) are rows of `code_write`, queued by the command in
its domain transaction and sent by the worker. The command returns the write;
its state is projected (queued, sending, failed) and shown on the item and
the pull request.

| Write             | Why a retry cannot duplicate it                                   |
| ----------------- | ----------------------------------------------------------------- |
| Create branch     | A branch that exists at the same commit counts as created         |
| Open pull request | The open pull request for the head branch is looked up first      |
| Comment           | A marker in the body is searched for before a retry posts again   |
| Merge             | Merging a merged pull request succeeds; the head must still match |
| Close, reopen     | Setting the state it has is a no-op on every host                 |

The `mutationId` of the command is the write's idempotency key: repeating a
request returns its first write, and reusing a key for a different request is
a conflict. A temporary failure (rate limit, unavailable) is retried with
backoff, five attempts in all; a refusal fails the write with the host's
reason, notifies the requester (`code_write_failed`) and waits for a person
to retry or cancel it (`codeWrite` state machine). A rejected credential marks
the connection as needing attention.

The host shows the connection's account as the author of what Lictory sends,
so comments are signed: "— Ada Lovelace, from Lictory", or "— Forge via Ada
Lovelace" for an agent. Pull requests Lictory opens record who asked
(`opened_by_id`) and the agent (`opened_via`); their description links back to
the work item.

## Authorization

| Who                                                                                    | May                                                                                                                                   |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Organization administrators (`canManageCodeHosts`)                                     | Connect, replace credentials, rotate webhook secrets, disconnect                                                                      |
| Project administrators (`canLinkRepository`)                                           | Link and unlink repositories to their project, browse a host's repositories                                                           |
| People with “Change properties” in a project the repository serves (`canWorkWithCode`) | Link and unlink code to that project's items, create branches, open, comment on, review, close and merge pull requests, import issues |
| Organization members                                                                   | Read everything the Code module projects                                                                                              |

Repositories, like projects, are organization-wide: there is no per-repository
read permission. The host's own protections (required reviews, branch
protection) apply on top of everything Lictory sends, because it acts with the
connection's identity.

A merge is a `decision` capability. Lictory refuses it from the state machine
(`codePullRequest`), for a draft, failing or running checks, requested changes
(on the host, or a current review recorded in Lictory) or conflicts
(`mergeBlockers` in `code/merge-rules.ts`, shared with the browser), and when
the head moved since the person looked (`expectedHeadSha`). When a work item
the pull request is linked to belongs to a project whose Definition of Done
requires CI (`definitionRequiresCi`, the default), a head the host reported
no checks for is refused too: no check is no evidence, for a person's merge
as for Autopilot's. Pull requests that deliver no such item merge without
reported checks, and the merge box says none were reported.
A second merge request while one is in flight returns the first.

## Projections

`code_entity` (`code/projections.ts`) is the Code module's projection table,
apart from `sync_entity` and `space_entity`, and in the `lictory_zero`
publication. Types: `codeConnection` (never the credential or secret),
`codeRepository`, `codePullRequest` (with its checks and the items it is
linked to), `codeIssue`, `codeLink` (with a summary of what it points at, for
the item's Code panel), `codeWrite` (queued, sending or failed only) and
`codeIdentity` (a person's login on a host, which they set themselves for the
"mine" and "review requested" filters and which grants nothing). Rows of an
archived connection leave the projection and return when the same host and
account are connected again.

Writers call `writeCodeProjections(tx, organizationId, touch)` naming what
they touched, inside the transaction and under the organization lock;
`rebuildCodeProjections` runs with `rebuildProjections`, and
`codeProjectionDrift` is the test invariant. Zero queries (`codeHosts`,
`codeList`, `codePullRequest`, `codeWrites`, `workItemCode`) authorize
through organization membership.

## Ports for other modules

Modules never read the code tables; they call these (`code/ports.ts`):

- **Definition of Done** (`createCodeEvidence(db)`):
  `linkedPullRequests(organizationId, workItemId)` returns each currently
  linked pull request with `merged`, `mergedAt`, `headSha`, `reviewDecision`,
  `approvedBy`, `openedById`, `openedVia`, the agent and session that opened
  it and its checks evidence; `checksForSha(organizationId, repositoryId,
sha)` says whether a commit's checks `passed` (and which fail or run);
  `pullRequest(organizationId, id)`; and `evidence(tx, organizationId,
workItemIds)`, the Claims `DeliveryEvidenceSource`, read with the claims
  transaction.
- **Autopilot** (`createCodeMergeExecutor(db)`): `requestMerge(tx, request)`
  is the Claims `CodeMergeExecutor` (below); `enqueueMerge` does the same in
  its own transaction and throws its refusal.
- **Agent sessions** (`resolveSessionWorkspace(db, { organizationId, userId,
repositoryId, branch })`): the clone URL, default branch and a credential
  for git over HTTPS (`username`, `token`, `expiresAt`, `longLived`). The
  session's accountable person must be able to work with the repository's
  code. The credential goes to the runner through the runner protocol, never
  into a transcript. `chooseSessionRepository` picks the repository (below).
- **Links from sessions**: `createCodeService(db).linkCode(actor, { …,
agentSessionId })` records `source: "agent_session"`.

## The code loop

`installCodeLoop(db)` (`code/loop.ts`, called by the API and the worker
after `installFactoryLoop`) installs Code's side of
[the factory loop](software-factory.md#claims-and-the-factory-loop):

```text
ready item ─dispatch─▶ session ─workspace─▶ runner clones the item's repository, pushes its branch
   ▲                                                         │ complete (branch)
   │                                                         ▼
 Done ◀─Definition of Done─ mirror ◀─ingest── host ◀─outbox── pull request (linked to item + session)
   ▲                          ▲                                   │ each new head
   │                          └──── review recorded in Lictory ◀── reviewer agent's session
   └── merge: a person (Build) or Autopilot (policy, its administrator)
```

| Port                                 | Where                     | Code's implementation                                                                                                       |
| ------------------------------------ | ------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `SessionWorkspaceResolver`           | Factory, runner request   | Chooses the repository, mints the credential, records the repository on the session                                         |
| `SessionCompletionListener`          | Factory, after completion | Opens the pushed branch's pull request through the outbox                                                                   |
| `DeliveryEvidenceSource`             | Claims, in transaction    | The mirror and reviews recorded in Lictory, as Definition of Done evidence                                                  |
| `CodeMergeExecutor`                  | Claims, in transaction    | Queues Autopilot's merge (and its comment) under the policy administrator's authority                                       |
| Code session hooks (`code/hooks.ts`) | Code's outbox and ingest  | Record a session's pull request (in the outbox transaction), show it in the thread and start review sessions (after commit) |

### Agent sessions

A session works in **the repository it names** (`repositoryId`, which must
serve the item's project; a person asking an agent in a channel names one by
its full name or address, `repositoryNamedIn`), else **the one whose clone address it states**,
else **its project's default** (`code_repository_project.is_default`, set
by a project administrator with `setDefaultCodeRepository`, one per
project), else **the project's first linked repository**. A session without
a project only uses a repository it names. An address that is not one of
the project's repositories is the session's own and gets no brokered
credential. The chosen repository is recorded on the session
(`agent_session.repository_id`, Code-owned text), so its pull request opens
there even if the default changes meanwhile.

The branch is named for the item and the session
(`lictory/pay-142-refund-retries-1a2b3c4d`: Code's branch suggestion plus
the session), so key detection links it and two sessions never share one.

### Pull requests from agent sessions

When a session completes and its runner reports a pushed branch, the Factory
calls the completion listener after the completion committed. Code opens the
pull request as the agent acting for its owner (`surface: runner`, the agent
and session on the write), for the session's work item (titled with its key,
the body is the session's summary and a link to it), through the outbox:

- **Idempotent by head branch and run.** The write's idempotency key is
  `session-pr:<session>:<attempt>`, so a repeated completion reuses the
  write, and the outbox looks for the branch's open pull request before
  opening one, so a retried run (or an agent that opened it on the host)
  finds the same pull request.
- **Another session's branch opens nothing.** A reviewer that pushed to the
  pull request it reviews does not open or claim it.
- **Provenance.** The mirror row records `opened_by_id`, `opened_via`, and
  `agent_id` and `agent_session_id`: the **Agent-authored** filter reads
  `agentAuthored` (opened through Lictory by an agent), never the host's
  author login. The link to the item has `source: agent_session` and the
  session.
- **The session learns it in the outbox's transaction.** That transaction
  holds the organization lock exclusively, which excludes every Factory
  writer, so it sets `agent_session.pull_request_id/url` and appends a
  status event there (`recordSessionPullRequest`). After commit the session's
  card links the pull request and the agent posts "Opened pull request …" in
  its thread, once (stable message id).

A refusal (the owner lost "Change properties", the repository stopped
serving the project) leaves the branch pushed and says why where people
look, once per attempt: an error in the session's log
(`recordSessionPullRequestRefused`), Lictory's note in the session's thread
and a `code_pull_request_refused` entry in the item's history. A person can
open the pull request from the item.

### Reviews recorded in Lictory

**Decision: an agent's review is Lictory's record, bound to the head
commit, and a signed comment shows it on the host.** Every write to a host
carries the connection's identity, so the host cannot say which agent
approved, and a GitHub App or token cannot approve a pull request it opened.
`reviewCodePullRequest` (`code_review`) records `approve` or
`request_changes` for the pull request's current head (`expectedHeadSha`
refuses a review of a head that moved), the accountable person and the
agent, supersedes the same reviewer's earlier review of that pull request
(history keeps it), queues the comment and re-evaluates the Definition of
Done. It needs "Change properties" in a project the repository serves and
the `review` step of the `codePullRequest` machine (open only). **An agent
never reviews its own pull request** (`agent_id` of the pull request).

**People review the same way.** The pull request page offers Approve and
Request changes to people who may work with the code; their review is
recorded like an agent's (reviewer, no agent), supersedes their earlier one
and is shown on the host, signed. `reviewState` joins the host's decision
and the current reviews recorded in Lictory (requested changes outweigh
approvals): the item's Code panel, the pull request list and board cards
read it, so no surface says "No reviews" beside a recorded approval. When
every approval is an agent's, the merge box says that no person has
reviewed the code.

The Definition of Done counts, per pull request, approvals of the head
commit from reviews recorded in Lictory (agent and person) and from the
host's approving logins (mapped to the people who set them as their login).
With a reviewer agent in the autonomy policy only that agent's approval of
the head counts; new commits need a new review.

**Review sessions.** After a pull request opened from a session is opened
or gets a new head (outbox, ingest, reconciliation), Code starts a session
for the project's reviewer agent when the project is on Build or Autopilot
and the reviewer is not the author: one per pull request head (its id
derives from both), as the reviewer's owner, on the pull request's branch
and repository, reporting to the policy's channel. Its prompt names the pull
request, its head and the tool to call.

### Evidence follows ingest

Ingest, reconciliation, the outbox (recording an opened, refreshed or merged
pull request) and recorded reviews call `followCodeEvidence(tx, …)` in their
transaction, under the organization lock: the items linked to the touched
pull requests are re-evaluated with `followDefinitionOfDone`, reading only
Lictory's rows. Passing items move to Done, Autopilot requests merges. A
failure there rolls back to a savepoint and is logged, never the mirror;
the dispatcher evaluates claimed work again on its next run.

### Autopilot's merge

`requestMerge` runs in the claims transaction (once per pull request head;
Claims records `autopilot_merge`). It queues the merge as a person's merge
would be refused (state, draft, failing or pending checks, requested
changes, conflicts, a head other than the one decided), with
`requested_by_id` the administrator who set the policy, who must still
administer the project the repository serves, and `performed_via`
"Autopilot · policy set by Ada Lovelace". A comment on the pull request
says what passed and under which policy version. When the host answers,
the mirror records `merge_requested_by_id` and `merged_via`, shown on the
pull request; a person's merge from Lictory records them too. Lowering the
level below Autopilot or the administrator losing the project stops it
(the refusal is recorded once per head).

## Failure without code hosts

Nothing else depends on a connection: the Code page explains what to connect,
the item's Code panel is hidden until a host is connected, and every other
module works as before. A host that is down delays mirrors (webhooks are
stored and retried; reconciliation repairs) and fails writes visibly with the
host's reason.
