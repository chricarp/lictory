title: Getting started

**Joining a team that already uses Lictory?** [Sign in](#sign-in), then skip
to [Write a first proposal](#write-a-first-proposal). The steps in between are
for whoever sets the team up.

**Setting it up?** Lictory runs on your own server: the first step installs
it, the rest happen at your installation's address (for example
`https://lictory.example.com`).

## From an empty server to delivered work

<Steps>
<Step>

### Install Lictory (administrators)

Follow [Install](/self-hosting/install) to set up a server with the `lictory`
command, then open its address in your browser. The
[overview](/self-hosting) lists what the server needs. To look around first,
[try Lictory on your computer](/self-hosting/try) with one command.

</Step>
<Step>

### Sign in

Open your installation's address and sign in the way you were invited: the
invitation email, your company's single sign-on, or an account you already
have. Then choose a handle, which teammates use to mention you (changeable
later in account settings).

<Callout title="For administrators">
  Sign in first with the administrator the installer created (`sudo lictory
  admin setup` adds one later), then invite people as the [access
  policy](/self-hosting/configuration#access-policy) allows.
</Callout>

</Step>
<Step>

### Create your first project

Open your organization and name its first project. The project **key**
becomes part of every identifier (`PAY-142`) and never changes; the name can.

Guided setup asks only what a team must decide before its first day:

- **Where does delivery happen?** _In Lictory_ (boards, backlog and
  iterations next to the specifications) or _In Jira_ (export ready work;
  Jira owns status and sprints). See [delivery](/concepts/delivery).
- **Lictory Intelligence**: whether AI may review specifications, chat and
  propose fixes. Everything works without it; on a server without an AI
  provider it starts off.
- **Invite people** (optional): invitees join the new project in the
  discipline you choose for each (Engineering by default), so reviews can be
  asked of them on day one.

Everything else starts from defaults. Work item types, the workflow and the
Product, Engineering and QA disciplines are created for you, and you become a
project administrator in Product. A project delivered in Lictory plans
continuously (a board and a ranked backlog) with story points, and work may
start before its specification is ready while Lictory records what was
missing ([readiness policy](/concepts/readiness#readiness-policy)). Change any
of it in **Project settings** (**Planning**, **Definition of Ready**).

Setup ends on **Home**, where a checklist (visible to administrators) carries
on: write a first proposal and invite your team, then connect a code host, a
runner and an agent and start a channel ([the Factory](/factory)).

<Callout title="More than one organization">
  Where the access policy lets everyone create organizations, people without one
  can create their own from the welcome page.
</Callout>

</Step>
<Step>

### Invite your team

1. In **Organization settings → Members**, invite people by email or Lictory
   username. They join the organization when they accept.
2. In **Project settings → Members** and **Disciplines**, add them to the
   project and the disciplines they work in: an engineer to Engineering, a
   tester to QA. Disciplines decide who can be asked to review and what each
   person may do with work items ([disciplines](/organization/disciplines)).

The invitation can also set the project and disciplines
([members](/organization/members)). People invited during setup are already in
the first project, in their chosen discipline. Someone who joins without a
discipline sees on Home that an administrator still has to give them one.

</Step>
<Step>

### Connect your code and a first agent (optional)

Each step stands alone; specifications, reviews and delivery work without
any of them.

1. **Connect a code host** (organization administrators): in **Organization
   settings → Code hosts**, connect GitHub, GitLab or Bitbucket, add the
   webhook it shows and link repositories to the project
   ([code hosts](/integrations/code-hosts)).
2. **Add a runner**: in **Factory → Runners**, create a registration token and
   run the command it shows on a machine you control
   ([runners](/factory/runners)).
3. **Create an agent**: in **Factory → Agents**, name it, choose its harness
   (Claude Code, Codex or the built-in one) and its scope. You are its owner
   and it acts with your permissions ([agents](/factory/agents)). Start a
   first session from **Factory → Start session**, or mention it in a
   channel.

How much agents do by themselves is the project's
[autonomy policy](/factory/autonomy), **Assist** by default.

</Step>
<Step>

### Write a first proposal

Open the project's **Proposals** and choose **New proposal**. Describe the
problem and the intended behavior; rough is fine. Add the sections reviewers
look for, such as _Acceptance criteria_ and _Failure behavior_. Type `#` to
mention another work item and `[[` to cite a page.

The text is a shared [live draft](/specifications/live-drafts): teammates edit
with you, and it saves as you type. **Save revision N** turns it into a
[revision](/specifications/history), the version people review.

</Step>
<Step>

### Request reviews

From the item's review rail (**Review & details** on a narrow screen),
**Request review** from the disciplines that need to agree, for example
Engineering and QA. Reviewers comment on the exact text, mark a discussion
**blocking** when it must be settled first, and **Approve** or **Request
changes** ([reviews](/review/requests)).

Revise until the open questions are settled, and record what you agreed as a
[decision](/specifications/decisions). Each material revision makes earlier
approvals stale and asks the same reviewers again, so an approval always
refers to the text actually reviewed ([approvals](/review/approvals)).

</Step>
<Step>

### Reach ready

When every [readiness check](/review/readiness) passes (by default: the
specification is written, no blocking discussion is open, and every required
review approved the current revision), the item becomes **ready**. Its main
text is then protected: further changes are
[proposed changes](/specifications/branches), drafted apart, reviewed and
applied as a new revision. A proposed change can also carry the
[breakdown](/delivery/breakdown) into Stories and Tasks.

</Step>
<Step>

### Deliver

- **In Lictory**: choose **Accept revision N for delivery** to record what
  the team agreed to build, plan it into a sprint or cycle and move it across
  the **Board**. Moving it to Done records the delivered revision. See
  [Deliver](/delivery). With the autonomy policy at **Build** or
  **Autopilot**, agents claim ready items themselves, open the pull request and
  report progress on the item ([autonomy](/factory/autonomy)).
- **In Jira**: connect a Jira site in **Organization settings →
  Integrations**, choose the Jira project and type mapping in **Project
  settings → Delivery**, then **Hand off** the ready work from the project's
  **Hand-off** view. See [Jira](/integrations/jira).

</Step>
</Steps>

## Write it down in Spaces

Knowledge that is not a work item (a runbook, how the team works, an
architecture note) belongs in a **space**.

1. Choose **New space** under **Spaces** in the sidebar and pick its location:
   the organization, a project or a team, whose members can then edit it.
2. Add a first page with **New page**. Teammates can edit it with you at the
   same time.
3. **Publish** makes it the version everyone reads; every version stays in the
   page's history.

Type `#` to mention a work item: the item then lists the page in its
**Knowledge**, and a specification can cite the page in turn
([knowledge](/knowledge)). The [Spaces guide](/spaces) covers the rest, from
comments to reviewed publishing.
