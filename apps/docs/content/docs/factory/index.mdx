---
title: The Factory
description: Start coding agents on runners you control, follow and steer their work, and answer what they ask.
---

The **Factory** is where your team's coding agents work. An agent such as
Claude Code, Codex or Lictory's built-in harness runs on a **runner**, a
machine you control, in its own git branch. People start, steer and decide;
agents do the work in between.

Open it from **Factory** in the sidebar. The overview shows:

- agent requests waiting on you, answered in place (the same rows as your
  [Inbox](/inbox)'s **To do** and Home)
- sessions waiting on a teammate, and on whom
- what agents are working on, what is queued and what finished recently

Its tabs lead to **Sessions**, **Agents** and **Runners**. **Sessions** lists
the organization's recent sessions, newest first, with who ran and started
each, how long it ran and how it ended. Filter by state, agent or who started
it.

## Before you start

1. [Add a runner](/factory/runners): a server, a VPS, a laptop or a Mac with
   `lictory-runner` installed.
2. [Create an agent](/factory/agents) you own, and choose its harness.

## Start a session

Choose **Start session**, pick the agent and say what it should do.
Optionally name a work item (its key goes into the branch name and commit
message, so the code links back to it) and a repository with its base
branch.

The session is **queued** until a runner that may run the agent claims it.
When no online runner can (none is online, none has the agent's harness, or
the only ones are other people's personal runners), the session, its card and
its item say **No runner** and the overview points you to **Runners**.

The repository defaults to the work item's project default. With no work item
and exactly one repository linked in the organization, it defaults to that
one; you can still choose **None**.

Without a repository the agent works in a scratch workspace discarded when
the session ends. The dialog says so before you start, and so does any
request to write a file or run a command. A command's effects outside the
workspace, such as a database migration, are not undone. A session that
changed files there ends as **Work not kept**, with the number of files
discarded, instead of **Completed**; **Start again with a repository…** opens
Start session with the same agent, task and work item.

You can start sessions with agents you own and with agents their owners share
with the organization. A shared agent still acts as its owner.

You can also mention the agent in a channel or direct message: the message's
thread becomes the session's thread, with a live card, the agent's answers
and its approval requests. See [ask an agent](/channels#ask-an-agent).

## Follow and steer

The session page shows the transcript live: messages, tool calls and commands
(folded to one line), changed files and status changes. Below it:

- **Message the agent** to steer it. A message sent while it works arrives
  when its current step ends.
- **Interrupt** stops the current turn; the agent keeps its work and waits
  for your next message (**Waiting on you**). Offered only while the agent
  works.
- **Cancel…** stops the session for good, after you confirm.
- **Retry** reruns a failed or canceled session from its original
  instructions, with the messages you sent before; its history stays.

Only the person who started the session and the agent's owner can steer it.
An organization administrator can also cancel it. In a session's channel
thread, their replies are messages to the agent, and **Interrupt** and
**Cancel…** are on the session's card.

## Answer what the agent asks

When an agent needs a decision, such as a command its harness may not run
without permission, the session is **Waiting on you**. The approval request
appears in the session, on the Factory overview, on Home and in your Inbox's
To do. It names the item, the agent and the exact action (the command or the
file). Open **Review** to see the evidence, then choose **Approve** or
**Deny**.

A request that names no command or file is a **Question**: answer it in words
(**Answer**, then **Send answer**) or deny it. Lictory never approves an
action on its title alone. Only the person who started the session and the
agent's owner can answer; an agent never answers for them.

When the agent asks something in its own words and waits, the session is
**Waiting on you** too: reply in the session or its thread.

A session you started that fails stays in your To do and on Home until you
retry it (or for a week). Retry runs the same task; to change the task,
update its work item or reply in its thread and start a new session (the
failed session's page links both).

## When it finishes

The runner commits what the agent left uncommitted, pushes the session's
branch and shows the agent's summary. **Completed** is the agent's claim, not
proof: work items reach done through merged pull requests, passing checks and
your Definition of Done.

If the runner stops responding, the session returns to the queue for another
runner (up to three attempts).

On a claimed item, the claim follows the session: the runner keeps it while
the session runs, a failed or canceled session gives the item back, and a
completed one keeps it until the Definition of Done moves the item to Done
(up to seven days; release it sooner if the work is abandoned).
