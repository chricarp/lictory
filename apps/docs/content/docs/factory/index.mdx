---
title: The Factory
description: Start coding agents on runners you control, follow their work live, steer them, answer what they ask and read what they changed.
---

The **Factory** is where your team's coding agents work. An agent such as
Claude Code, Codex or Lictory's built-in harness runs on a **runner**, a
machine you control, in its own git branch. People start sessions, steer
them and make the decisions; agents do the work in between.

Open it from **Factory** in the sidebar. The overview shows how many agent
requests wait on you (you answer them in the [Inbox](/inbox)'s **To do**,
or on the session's page), what agents are working on now, what is queued
and what finished recently. Its tabs lead to **Sessions**, **Agents** and
**Runners**; **Sessions** lists the recent sessions of the organization, so
you can find yesterday's run or the ones that failed.

## Before you start

1. [Add a runner](/factory/runners): a server, a VPS, a laptop or a Mac with
   `lictory-runner` installed.
2. [Create an agent](/factory/agents) you own, and choose the harness it
   runs.

## Start a session

Choose **Start session**, pick the agent and say what it should do. You can
name a work item (its key becomes part of the branch name and of the commit
message, so the code links back to it) and a repository with its base
branch. The session is **queued** until a runner that may run the agent
claims it. When no online runner can run it (none is online, none has the
agent's harness, or the only ones are other people's personal runners), the
session, its card and its item say **No runner** and the overview points
you to **Runners**.

You can start sessions with agents you own, and with agents their owners
share with the organization. A shared agent still acts as its owner.

You can also start one from a conversation: mention the agent in a channel
or a direct message and the message's thread becomes the session's thread,
with a live card, the agent's answers and its approval requests. See
[ask an agent](/channels#ask-an-agent).

## Follow and steer

The session page shows the transcript as it happens: the agent's messages,
tool calls and commands (folded to one line; open them for the details),
files it changed and status changes. Below it:

- **Message the agent** to steer it. A message sent while it works reaches
  it when its current step ends.
- **Interrupt** stops the current turn; the agent keeps its work and waits
  for your next message (the session shows **Waiting on you**).
- **Cancel** stops the session for good. **Retry** runs a failed or canceled
  session again from its original instructions and sends it the messages you
  sent before, so you do not repeat them; its history stays.

Only the person who started the session and the agent's owner can steer it.
An organization administrator can also cancel it. In a session's channel
thread, their replies are messages to the agent too.

## Answer what the agent asks

When an agent needs a decision (for example a command its harness may not
run without permission) the session is **Waiting on you** and an approval
request appears in the session, on the Factory overview, on Home and in your
Inbox's To do. It names the item, the agent and the exact action (the
command it would run or the file it would write); open **Review** to see the
evidence, then choose **Approve** or **Deny**. Only the person who started the
session and the agent's owner can answer, and an agent can never answer for
them.

When the agent asks something in its own words and waits for your answer,
the session is **Waiting on you** too: reply in the session or in its
thread.

A session you started that fails is in your To do and on Home until you
retry it (or for a week).

## When it finishes

The runner commits what the agent left uncommitted, pushes the session's
branch and shows the agent's summary. **Completed** is the agent's claim,
not proof: work items reach done through merged pull requests, passing
checks and your Definition of Done.

If the runner stops responding, the session returns to the queue and
another runner takes it (up to three attempts).

When the session works on a claimed item, the claim follows it: the runner
keeps the claim while the session runs, a failed or canceled session gives
the item back, and a completed one keeps the claim until the item's
Definition of Done moves it to Done (for up to seven days; release it sooner
if the work is abandoned).
