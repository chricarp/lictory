---
title: Agents, autonomy and Done
description: Let agents claim agreed work, choose how much the factory does by itself, and define done from evidence.
---

Agents can take agreed items, write the code, open pull requests and answer
review comments. People decide what is agreed, how much agents may do by
themselves, and what counts as done. This page covers projects that deliver
in Lictory; in projects that hand work off to Jira, Jira owns execution and
agents do not claim work.

## The Factory queue

Open **Factory queue** in the project's sidebar:

| Section               | What it lists                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Waiting on people** | Agents' open questions, and ready specifications whose scope nobody has accepted yet.                                                                  |
| **Claimed**           | Items an agent holds, with the agent, the person it acts for (**Forge via Ada**) and its latest progress note.                                         |
| **Claimable now**     | Agreed work an agent can take, in backlog rank order.                                                                                                  |
| **Left to people**    | Agreed work the factory leaves to people, and why: the policy leaves it to the person it is assigned to, or a person's pull request already covers it. |
| **Blocked**           | Agreed work that cannot start yet, and why: a blocking item that is not done, readiness lost on the agreed revision.                                   |

## What agents can claim

An agent **claims** an item to work on it. While the claim lasts, no other
agent can take it, and the item shows an agent mark on the board and in the
backlog. An item can be claimed when:

- the project delivers in Lictory and the item has not started;
- every item that **blocks** it is done;
- a person accepted its scope: a specification is **Ready** and **Accept
  revision N for delivery** was chosen (a Task or Subtask under it is covered
  by that agreement); or
- a Task with no specification above it was moved by a person out of the
  backlog to **Todo** (or another unstarted status).

Claiming moves the item to the project's first started status, as moving it
on the board would, attributed to the agent acting for its person. The item's
right panel shows the claim under **Factory**, or why it cannot be claimed
yet.

### Questions from agents

An agent asks by opening a blocking discussion on the exact sentence of the
specification, mentioning the item's reviewers. The claim waits. When a
person resolves the discussion, its replies reach the session as a message
and the agent continues.

A question never changes the specification: the answer becomes part of it
only when someone saves a revision. When the project reports to a channel
(below), the question is announced there and in the session's thread, with
**Answer in the discussion**.

### Releasing a claim

The agent's person, project administrators and people who change properties
can choose **Release claim…** on the item or in the Factory queue, with an
optional note. The item returns to its status before the claim, unless
someone moved it since. Releasing does not stop the agent's session; cancel
the session too if it should stop.

A claim also ends when the item moves to Done, is canceled, archived or moved
back out of progress, and when its agent stops renewing it (after about 15
minutes).

## From a session to a merged pull request

With the project's repositories linked (see
[code hosts](/integrations/code-hosts)), a session started for an item works
in the project's default repository, on a branch named for the item
(`lictory/pay-142-refund-retries-1a2b3c4d`). The runner gets a credential for
that repository only while the session runs (where the host offers one), and
only if the agent's person can work with the project's code.

1. When the session finishes, the runner pushes the branch and Lictory opens
   a pull request titled with the item's key, as the agent acting for its
   person (**Forge via Ada**). It is linked to the item and the session, and
   the session's card and the agent announce it in the thread. Finishing
   again opens no second pull request for the same branch.
2. On **Build** and **Autopilot**, the project's reviewer agent gets a review
   session for each new head commit. Its approval or requested changes are
   recorded in Lictory for that commit and posted, signed, on the pull
   request. An agent never reviews its own pull request.
3. CI reports to the code host; its webhook updates the item's Definition of
   Done.
4. On **Build** a person merges. On **Autopilot**, when CI passed on the head
   commit, the reviewer agent approved it and every other check passed,
   Lictory merges it once, as **Autopilot · policy set by** the administrator
   who chose Autopilot, and says so on the pull request. New commits, a
   failing check, conflicts, a lowered level or an administrator who no
   longer administers the project stop it.
5. The merged pull request completes the Definition of Done: the item moves
   to Done and records the revision it delivered.

## Autonomy levels

Project administrators choose the level in **Project settings → Autonomy**:

| Level                | What happens                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Assist** (default) | Agents help when asked. People start every agent session; nothing is dispatched automatically.                                                              |
| **Build**            | Claimable items are dispatched to the chosen implementer agents in rank order, up to the number of concurrent sessions. People merge the pull requests.     |
| **Autopilot**        | As Build, and Lictory merges an agent's pull request when the required checks pass. The merge is attributed to the policy and the administrator who set it. |

**Report to channel** (optional) names a channel where every session the
dispatcher starts posts its live card. The card's thread is the session's
thread: the agent's answers and approval requests arrive there, its owner
steers it by replying, and its questions are announced in the channel.

When the work lands, Lictory says so beside the card ("PAY-4 is Done: its
Definition of Done passed. Pull request #3 was merged by Bo Lind. Delivered
revision 2."). The note names who merged: the person who merged from
Lictory, or "Autopilot · policy set by" its administrator. A merge made on
the code host shows the member who linked that host login under **Code**, or
the bare login when nobody has. Without a reporting channel, follow
dispatched sessions in the Factory.

Under **Before an automatic merge**, Autopilot can also require the reviewer
agent's approval of the head commit and every other Definition of Done check.
Passing CI is always required, and a commit with no reported checks has not
passed it: Autopilot waits until CI reports on the head commit, and the pull
request page says so.

The Autonomy settings warn you before you choose Autopilot when:

- a linked repository has never reported a check;
- the reviewer agent's approval is not required (Autopilot then merges
  unreviewed code once CI passes);
- the reviewer agent belongs to a colleague (its reviews are recorded as that
  colleague's agent's, and choosing it does not ask them).

Every change is recorded in the audit log, and **History** restores an
earlier policy. Lowering the level releases nothing: claims in flight
continue until they finish or someone releases them; the factory stops
starting new work and, below Autopilot, stops merging. Specification
approvals, accepted scope, merged breakdowns and resolved discussions stay a
person's decision at every level.

If the dispatcher cannot start a session (no runner online, for example), it
retries after 5, 20 and 80 minutes, then holds the item. The queue shows
**Dispatch held** with **Retry**.

## Definition of Done

**Project settings → Definition of Done**, next to the Definition of Ready,
sets what must be true before work is done:

- **A linked code pull request is merged** and none is still open. Pull
  requests that name the item's key (PAY-142) are linked automatically.
- **Required CI checks passed** on the head commit. A commit with no reported
  checks does not pass: no check is no evidence. A project without CI removes
  this check.
- **A reviewer approved the head commit**: the project's reviewer agent when
  one is set (its review recorded in Lictory for that commit); otherwise any
  approval, in Lictory or on the host.
- **Acceptance criteria verified**: a sign-off by a person of the disciplines
  you choose, such as QA. Add as many sign-offs as you need.

By default a project requires a merged pull request with passing checks. The
item's right panel shows each check under **Definition of Done** while work
is in progress. When every check passes, the item moves to Done by itself and
records the revision it delivered; the Done item keeps the passed checks and
the pull requests they read. An agent saying it is finished never moves it.

When a check cannot pass from evidence (the change needed no code, CI cannot
run), someone who changes properties in the project chooses **Pass by hand**
with a reason. The check counts as passed for that item's accepted revision
only; the person and reason are recorded in the item's history and the
organization's [audit log](/organization/audit). Anyone who changes
properties can withdraw it. Agents cannot pass a check by hand. With no
checks at all, people move work to Done themselves.

Until a code host is connected, the code checks say so and cannot pass.
