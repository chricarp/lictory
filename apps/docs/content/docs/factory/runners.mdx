title: Runners
description: Install lictory-runner on a server, VPS, laptop or Mac, register it with a one-time token and keep it running as a service.
---

A **runner** is a machine that runs agent sessions. It connects out to
Lictory over HTTPS, so it needs no open port and works behind NAT, proxies
and firewalls that allow outbound HTTPS. Each session works in its own git
worktree; a runner can also run each session in a Docker container.

- An **organization runner** runs any agent of the organization. An
  organization administrator adds it.
- A **personal runner** runs only your own agents, for example on your
  laptop. Any member can add one.

## Add a runner

1. Open **Factory → Runners** and choose **Add runner**.
2. Choose an organization or a personal runner and **Create registration
   token**. The token works once and expires after an hour.
3. Copy the command for your system and run it on the machine. It downloads
   `lictory-runner` of your server's release, checks it against the
   release's checksums, registers it and installs it as a service:

```sh
curl -fsSL https://github.com/chricarp/lictory/releases/latest/download/lictory-runner-install.sh | sh -s -- \
  --version <server release> --url https://lictory.example.com --token lrt_… --service
```

On Windows, in PowerShell:

```powershell
& ([scriptblock]::Create((irm https://github.com/chricarp/lictory/releases/latest/download/lictory-runner-install.ps1))) `
  -Version <server release> -Url https://lictory.example.com -Token lrt_… -Service
```

The dialog fills in your server's release, address and token. A release
published before runner downloads existed carries none of these files, and
`curl` then reports a 404: build the runner from source instead
([lictory.com/download](https://lictory.com/download#runner-source) lists the
three commands) and register it with `lictory-runner register`.

The installer puts `lictory-runner` in `/usr/local/bin` when it can write
there and in `~/.local/bin` otherwise (`--dir` chooses another directory);
on Windows in `%LOCALAPPDATA%\Programs\lictory-runner`, which it adds to your
`PATH`. Without `--url` and `--token` it only installs and prints the
commands to register:

```sh
lictory-runner register --url https://lictory.example.com --token lrt_…
lictory-runner install-service --enable
```

The runner appears in the list as soon as it registers and shows **Online**
while it is connected.

To install the newest stable release by hand, or download a binary for
another machine, see [lictory.com/download](https://lictory.com/download#runner).

Install the harnesses its agents use on the same machine: Claude Code
(`claude`) or Codex (`codex`), signed in with your own subscription or API
key. The built-in harness needs nothing on the machine: it uses the
organization's Lictory Intelligence model through the server.

## Commands

| Command                          | What it does                                                          |
| -------------------------------- | --------------------------------------------------------------------- |
| `lictory-runner register`        | Exchanges a registration token for the runner's credential            |
| `lictory-runner start`           | Connects and runs sessions until stopped (Ctrl-C hands them back)     |
| `lictory-runner status`          | Shows whether the runner is running and what it is working on         |
| `lictory-runner doctor`          | Checks the server, the credential, git, harnesses, Docker and clock   |
| `lictory-runner install-service` | A systemd unit (Linux) or launchd agent (macOS); `--enable` starts it |

`register` accepts `--name`, `--max-sessions <n>` (default 2),
`--isolation host|container`, `--container-image <image>` and
`--label <label>`. On Linux a user service
stops when you log out unless lingering is on (`loginctl enable-linger`);
`--system` installs a system service instead. On Windows,
`install-service` prints the Task Scheduler commands.

The configuration and credential are in `~/.config/lictory-runner` on Linux,
`~/Library/Application Support/lictory-runner` on macOS and
`%APPDATA%\lictory-runner` on Windows (`LICTORY_RUNNER_HOME` overrides
it), readable only by your account. `config.json` also holds
`claudePermissionMode` (what Claude Code may do without asking, default
`acceptEdits`), `codexSandbox` (default `workspace-write`),
`containerImage` and `keepWorktrees`.

### Container isolation

With `--isolation container` each session runs in its own Docker container
with only its worktree mounted. Lictory publishes no sandbox image: build one
that contains git and the harnesses your agents use, push it to a registry
you trust and register with
`--container-image registry.example.com/runner-sandbox@sha256:…`. Pin it by
digest: a tag can be moved to other contents, a digest cannot.
`lictory-runner doctor` warns about an image that is not pinned.

## Operate many runners

- **Capacity:** `--max-sessions` sets how many sessions run at once (default
  2). Sessions waiting for a person's answer keep their lease without taking
  a slot. Add runners rather than raising the number on one machine.
- **Which agents run where:** a session can name a runner, an agent can have
  a default runner, and a personal runner runs only its owner's agents.
  Labels describe the machine; they do not route sessions.
- **Updates:** run the installer again on each machine without a token (see
  below), then restart the service. Keep runners on the server's release:
  the add-runner command pins it.
- **Maintenance:** stop the service (`systemctl stop lictory-runner`, or
  Ctrl-C). The runner stops claiming, hands its running sessions back to the
  queue and exits; another runner picks them up. Start it again afterwards.
  To retire a machine for good, revoke it.
- **Monitoring:** the server's monitor alerts when an organization runner has
  been offline for ten minutes, when sessions wait 15 minutes with no online
  runner that can take them, and when every capable runner is busy for an
  hour ([monitoring](/self-hosting/monitoring)). Personal runners are not
  alerted on.
- **Revoked runners:** a revoked runner exits with status 2. The systemd unit
  that `install-service` writes does not restart it; register it again to
  bring it back.

## Update a runner

Run the installer again with the new version (or without `--version` for
the latest stable release) and without a token: it replaces the binary in
place. A runner running as a service keeps the old version until it
restarts (`systemctl --user restart lictory-runner` on Linux,
`launchctl kickstart -k gui/$(id -u)/com.lictory.runner` on macOS).

## Verify a download

Every release lists the SHA-256 of each file in `SHA256SUMS`, which the
installers check. The files are also signed by the release workflow:
`gh attestation verify <downloaded file> --repo chricarp/lictory` (for
example `lictory-runner-linux-x64`) checks a downloaded binary, and `cosign verify-blob` checks `SHA256SUMS`
against `SHA256SUMS.sigstore.json` (see the
[release documentation](https://github.com/chricarp/lictory/blob/main/docs/operations/releases.md#runner-and-desktop-app)).

## Revoke a runner

Choose the trash icon next to the runner. Its credential stops working at
once and the sessions it was running return to the queue. A personal runner
also stops working when its owner leaves the organization.
