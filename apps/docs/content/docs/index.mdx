Lictory is a work-management platform for software teams. What sets it apart
is what happens **before** development: specifications are drafted, reviewed,
discussed, revised and approved the way code changes are, so a team can go
from _"Product wants to build this"_ to _"Engineering can safely commit to
building this"_ without a meeting for every requirement.

## Requirements, reviewed like code

A specification in Lictory is not a document with comments. It has
[revisions](/concepts/specifications), reviewers, discussions anchored to the
text, proposed changes, [approvals that belong to the revision they
reviewed](/concepts/reviews), and [readiness checks](/concepts/readiness)
that work like CI for requirements. At any time you can see what changed, who
changed it, who approved which revision and what is still unresolved.

Product, Engineering, QA and any other discipline a project configures take
part as equals: each reviews the concerns it owns. Lictory Intelligence can
point out gaps, contradictions and missing scenarios and propose changes, but
people decide what becomes part of the specification. Lictory works fully
without AI.

## Two ways to deliver

Every project chooses its delivery mode. The refinement workflow is the same
in both.

| Mode                 | Refinement | Delivery                                                               |
| -------------------- | ---------- | ---------------------------------------------------------------------- |
| **Native (Lictory)** | Lictory    | Lictory: work item types, workflows, board, backlog, sprints or cycles |
| **External (Jira)**  | Lictory    | Jira: ready work is handed off, Jira's status is read back             |

Exactly one system owns delivery for a project's work, so nothing is tracked
twice. See [delivery](/concepts/delivery).
