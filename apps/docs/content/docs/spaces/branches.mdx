A **branch** is a proposed change to one page, with its own live draft. A
**pull request** proposes merging it into the published page (or another
branch) and is where it is reviewed. In a
[Reviewed space](/spaces/publishing#reviewed-spaces) this is the only way to
publish; in a Direct space it is for bigger changes worth a review.

## Start a branch

Anyone who can edit the space can start a branch:

- In a Reviewed space, **Start a branch** on the page branches from the
  published version and opens its draft.
- In any space, **Start a branch** under **Version history → Branches**
  takes a **Branch name** and **Start from**: the **Current main version**
  or any earlier one (to bring an old version back through review).
- From a work item, **Propose page update** in its **Knowledge** section
  opens a branch of the chosen page, named after the change and linked to
  the item's current revision ([propose a page
  update](/knowledge/in-work#propose-a-page-update)). Its pull request takes
  the change as default title, and the item follows it until it merges.

Once a page has more than one line, a **branch switcher** appears in the
header: main (_Published_, and whether its draft has unpublished changes),
each branch with its author, _uncommitted changes_ and _pull request_, plus
**All branches** and **Pull requests**. Everyone who can read the space can
read any branch's latest commit. **Version history → Branches** lists the
same lines with who started each, _in review_ for an open pull request, and
**Open**.

### Collaborators

A branch belongs to its author, who can **Add collaborator** (anyone with
edit access to the space) and **Remove** them in **Version history →
Branches**. Author and collaborators edit, commit, sync and open pull
requests.

## Commit

**Commit** turns what the server stored into the branch's next version, as
**Publish** does on main. Add an optional message, then:

- **Commit and send for review**, while the branch has no open pull request:
  commits, opens a pull request into main titled with the message's first
  line (or the page title), and asks the **Reviewer** chosen in the form
  (suggested as in the pull request form below).
- **Commit only** (or **Commit now** once a pull request is open): the
  version joins the branch, and an open pull request shows it.

The editor then says _Committed version N_, or _No changes to commit_ when
nothing changed. Edits typed afterwards stay **Uncommitted changes**.

Readers see nothing yet. **View pull request** opens the branch's pull
request, or after **Commit only**, **Open pull request** opens the form below
with this branch chosen.

Only commits are reviewed: a pull request shows the latest commit, never the
live draft, and a merge waits until the branch has no uncommitted changes.

## Pull requests

In **Version history → Pull requests**, **Create pull request** asks for:

- the **Source branch** (one you author or collaborate on);
- the **Target branch**: **main**, the published page, or another branch;
- a **Title** and a **Description**;
- a **Reviewer**, suggested as the author of the target's latest version, or
  else the page's latest other author. In a Reviewed space the form warns
  when a pull request ready for review would ask nobody;
- **Start as draft**, to share it before asking for reviews.

![A page pull request: its title and description, the resulting changes with the added Automatic retries section, and the review summary with Dev Patel required and Pending, Add reviewer, and the merge check “Requires approval from Dev Patel” above a disabled Merge pull request…](/screenshots/spaces-pull-request.webp)

A pull request shows:

- **Resulting changes**: what merging would change on the target
  (**Current** and **Proposed**), compared like
  [versions](/spaces/history#compare-two-versions);
- the **Review summary**: its state (**Open**, **Draft**, **Conflicts to
  resolve**, **Ready to merge** or **Merged**), the reviewers and the
  **Merge checks**.

Its actions menu (**⋯**) has **Edit details**, **Mark as draft** or **Ready
for review**, and **Close pull request…**. In a Reviewed space, **Pull
requests** on the space's home lists the open ones across all its pages,
marking those that wait for your review.

### Reviewers

**Add reviewer** (or **Request required review** for the first one) notifies
the person; anyone with comment or edit access can be asked. Each reviewer
shows **Required**, their state (**Pending**, **Approved**, **Changes
requested** or **Review outdated**) and when they were asked; **Cancel
request** withdraws it.

Reviewers **Approve** or **Request changes**, and can **Revoke decision**. A
new decision replaces the previous one.

Anyone who authored or typed in a commit the change brings in cannot approve
it (_Contributors cannot approve their own changes._), nor can agents acting
for them. There is no exception for a team of one: use a Direct space.

### Approvals belong to the exact result

An approval records the exact merged title and content the reviewer
inspected, computed from the branch and target as they were. _Approval is
required for this exact result._

When the result changes (a new commit on the branch, a new version on main,
a sync), the approval goes **stale**: **Review outdated**, _Approved an
earlier result_, and the reviewer is notified. Changes that leave the result
identical keep the approval. A stale approval never counts toward merging;
old decisions stay in the history.

## Merge

**Merge checks** list everything still in the way:

| Check                                                    | What to do                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| _Mark this pull request ready for review_                | It is a draft: choose **Ready for review**                                                 |
| _Commit or discard live changes on branch …_             | Commit the branch's draft (or the target's, in a Direct space: publish it)                 |
| _Resolve conflicts on the source branch_                 | See [conflicts](#conflicts)                                                                |
| _Resolve N blocking discussion(s)_                       | Resolve the blocking comments on the page ([comments](/spaces/comments#blocking-comments)) |
| _Request at least one required review_                   | Reviewed spaces only: ask someone for a required review                                    |
| _Requires approval from …_                               | Every required reviewer must approve the current result                                    |
| _Address the requested changes and ask for review again_ | A reviewer requests changes: commit the fix; they approve or revoke their decision         |
| _No changes remain to merge_                             | The target already contains everything; close the pull request                             |

At _All merge checks pass_, **Merge pull request…** becomes available: to
the space's editors for main, to the target branch's author and
collaborators for a branch. A Direct space requires no review, but a request
for changes or a blocking discussion still stops the merge.

The confirmation says whether the source branch is deleted (_Branch … will
be deleted after the merge._ or _… stays available after the merge._) and how
many discussions the merge deletes
([when a branch ends](#when-a-branch-ends)). Choose **Confirm merge**, or
**Merge and delete discussions**.

Merging into **main** publishes the next version with its valid approvals
(**Approved** in a Reviewed space, **Reviewed by** in a Direct one),
restarts main's live draft in a Direct space, and retires the source branch
unless another open pull request uses it. Merging into **another branch**
only moves that branch.

## Conflicts

When both sides changed since they split, Lictory combines non-overlapping
changes and counts identical ones once. Overlapping changes become
**conflicts**, each on the smallest piece decidable alone: a paragraph or
heading, a whole list, a whole table, or the title.

A pull request with **Conflicts to resolve** cannot be reviewed or merged.
On the source branch, choose **Resolve conflicts**.

1. Each conflict shows three columns: **Base** (the version both sides
   started from), **Ours** (your branch) and **Theirs** (the target).
2. Choose **Use ours**, **Use theirs**, **Use both** (not for the title) or
   **Edit manually**, which takes the resolved text in Markdown.
3. **Sync branch** applies your choices as a new commit on the branch and
   restarts its live draft from it.

Reviewers then approve the new result. If either side moved while you were
resolving, the sync is refused: **Reload preview** and look again.

When a branch and its target have no single common version (rare, after
unusual merges), they cannot be merged; restore the version you want on a
new branch instead.

## Sync a branch with main

**Sync from main** in **Version history → Branches** (author and
collaborators) takes in what was published meanwhile, in the same dialog:
_No conflicts. Sync main into …_, conflicts to resolve as above, or _Your
branch already includes the target version._ A sync is a commit that
restarts the live draft; editors move to the new content and keep unsaved
text ([when the draft is replaced](/spaces/editing#when-the-draft-is-replaced)).

## Close, delete and undo

Nothing in a page's versions is ever rewritten:

- **Revoke decision** withdraws an approval or a request for changes;
  **Cancel request** withdraws a review request.
- **Mark as draft** takes a pull request back out of review; **Close pull
  request…** closes it for good. A closed pull request keeps its reviews, and
  its open discussions are resolved, each recorded.
- **Delete branch…** (its author or an editor of the space) disconnects its
  editors and removes it; its commits stay in history, its discussions are
  deleted ([when a branch ends](#when-a-branch-ends)). Close its open pull
  requests first. A deleted branch cannot be restored; start a new one from
  its last version.

## When a branch ends

A discussion belongs to the line it was written on. When a branch is deleted
or retired by a merge, **its discussions are deleted with it**, open and
resolved, blocking and non-blocking, with every reply: left behind, they
could not be acted on and would block merges forever. Lictory deletes
discussions in no other case.

| What happens                           | Deleted                                                                                | Kept                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Delete branch…**                     | Every discussion on the branch and on pull requests from it                            | Discussions on main and on other branches                   |
| A merge that deletes the source branch | The same, and the pull request's own discussions                                       | Discussions on the target and other branches                |
| A merge that keeps the source branch   | Discussions on the source not tied to another pull request, and the pull request's own | The source's other pull requests' discussions, the target's |
| **Close pull request…**                | Nothing: its open discussions are resolved, each recorded                              | Everything                                                  |

The delete and merge confirmations say how many discussions go, by state,
and that this cannot be undone (_This permanently deletes … on this branch,
with all their replies._). If the count changes meanwhile, the confirmation
says so; cancel and reopen it. A merge never deletes an open blocking
discussion: it must be resolved first.

To keep a conclusion, record it before the branch ends: in a resolving
reply, in the page, or as a [decision](/specifications/decisions) on the
work item.

## Tips

- When delivered work changes behavior, use **Propose page update** on the
  work item, so the page's history names the item and revision.
- Keep a branch to one change: every new commit asks reviewers to look
  again.
