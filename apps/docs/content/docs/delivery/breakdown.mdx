---
title: Break down a specification
description: Split an agreed specification into Stories, Tasks and Subtasks, directly or as a reviewed breakdown that is approved with the specification.
---

A specification's **children** say how the team will build it: Stories
under an Epic, Tasks under a Story, Subtasks under a Task. Each child is an
ordinary work item with its own identifier, status and owner, and records the
parent revision it was derived from.

Add children in two ways:

- **Directly**, from the item's **Children** section, for work the team
  shapes as it goes.
- **As a reviewed breakdown**, proposed on a branch and approved with the
  specification, when reviewers should agree on the split before anyone
  starts.

## When to use it

- An Epic or Story is ready and the team needs pieces it can pick up.
- Engineering proposes how the work splits, and Product and QA should see
  it before it lands.
- An existing breakdown no longer fits the specification: children need to
  move, be detached or be archived.

## Add children directly

<Steps>
<Step>

### Open the parent

The item's **Children** section shows each child's status, how many are
done (`3/5 done`), how many spec-backed children are ready and the sum of
their estimates.

</Step>
<Step>

### Add a child

Choose **Add story** (the button names the child type; the type button
beside the title picks another, among types below the parent). Type a title;
`Enter` adds another, `Esc` finishes.

</Step>
<Step>

### Order the children

Drag a row by its handle, or focus it and press `Alt ↑` / `Alt ↓`.

</Step>
</Steps>

Children added directly record the parent's current revision. When the
parent changes later, the section counts children _from an earlier revision_
so you can check they still match.

Adding children never changes the specification, so a ready specification
stays ready while you prepare them.

## Propose a reviewed breakdown

<Steps>
<Step>

### Start the breakdown

In a specification's **Children** section, choose **Propose breakdown**.
Lictory opens your breakdown proposal (new or the one you started before).
It is a [branch](/specifications/branches) named `breakdown`, but you don't
need to know how branches work.

</Step>
<Step>

### Propose new children

Under **Proposed breakdown**, pick a **Child type**, write a **Title** and a
**Description** (behavior, scope, acceptance criteria), and choose **Propose
child**. Up to 100 per branch. You can edit the specification text in the
same change.

</Step>
<Step>

### Propose changes to existing children

Under **Change an existing child**, choose a child and what should happen to
it, then **Propose change**:

- **Move under another item**: an item higher in the hierarchy, or a child
  proposed in the same breakdown;
- **Detach from this parent**;
- **Archive**;
- **Rename (work without a specification)**: a new title for plain work.

Only children nobody has accepted, started, finished or canceled are
offered.

</Step>
<Step>

### Send it for review

Choose **Send for review**. Lictory saves your edits and asks the
specification's reviewers in one step; there is no commit message or pull
request to write. Reviewers see the specification changes and the
**Proposed breakdown** together. **Update the review** sends later edits and
asks them again.

</Step>
<Step>

### Create the items

Once the required reviews approve, choose **Create the items**. New
children are created and record the parent revision the breakdown produced;
changes to existing children apply at the same moment.

</Step>
</Steps>

### What reviewers approve

Approvals cover the whole merge, so changing only the proposed children
needs a fresh review. Until the merge, proposed children exist only on the
branch.

## Changes that are refused at merge

Each proposed change remembers the child's revision it was written
against. Merge applies it only while the child:

- still has that revision;
- is still a child of this item and not archived;
- has not been accepted for delivery, started, finished, canceled or handed
  off.

Otherwise the merge is refused and names the child, so nothing that changed
meanwhile is overwritten. The branch warns you beforehand. Drop the change and
propose it again against the child as it is now.

Archiving is also refused while the child has active children: archive or
move them first.

## Subtasks

Subtasks are the lowest level; add them from a Task's or Bug's **Children**
section. Boards and backlogs show a parent's progress (`2/4 done`), and the
[item preview](/delivery/relations#preview-an-item) shows **Subtasks done**.

## What to watch for

- **Spec-backed children keep their own text.** A breakdown can move,
  detach or archive a Story; its specification changes on the Story itself,
  approved by its own reviewers. Rename applies only to plain work.
- **Some changes stay outside the breakdown.** Type, relations, owners,
  ranking and iterations are changed on the items themselves.
- **Each change applies once.** Applied changes and created children stay in
  the commit history, so a later branch cannot create the same children
  again.
- **Archiving is reversible.** An archived child can be restored from its
  item page. See [organize work](/delivery/organize#archive-and-restore).

## Tips

- Propose a reviewed breakdown when reviewers care about the split (a risky
  migration, work spread across teams).
- Put acceptance criteria in each child's description so QA can review the
  breakdown for gaps.
- When the parent is amended, check children marked _from an earlier
  revision_ before accepting the new revision for delivery.
