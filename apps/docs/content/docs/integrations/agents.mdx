---
title: AI agents and MCP
description: Connect a terminal or editor agent to Lictory, read specifications and pages, propose reviewed changes and compare readings of done, using your own permissions.
---

Lictory exposes an MCP server so a coding agent in your terminal or editor can
work with the same specifications, discussions, delivery items and pages you
see in the browser. The connection uses your agent client's model; it does not require
Lictory Intelligence or an OpenAI key on the Lictory server.

The `lictory` server administration command is a separate tool. Use the
[terminal guide](/self-hosting/terminal) to install, upgrade or recover a server.

## Connect your agent

1. In Lictory, open **Account settings → AI agents (MCP)**.
2. Choose **New token**, give it an **Agent name**, select **Read & write** or
   **Read only**, and choose when it **Expires** (7, 30 or 90 days, 1 year,
   or no expiry). A token is a named agent: create one per agent so activity
   is attributable.
3. Copy the token immediately; it is shown only once.
4. In your MCP client's remote-server settings, use your installation's endpoint
   and a bearer header:

| Setting   | Value                                 |
| --------- | ------------------------------------- |
| Transport | Streamable HTTP                       |
| URL       | `https://<your-lictory-host>/api/mcp` |
| Header    | `Authorization: Bearer <your-token>`  |

The endpoint is also displayed in Account settings. Store the token in the
client's private credential configuration, outside version control. It can
access the organizations you belong to, subject to your current permissions
and the token's access level. It is not an organization-scoped credential.

Client configuration formats differ. Choose a client that supports a remote
Streamable HTTP server and custom authorization headers. Lictory uses personal
tokens for this connection; signing into Lictory in a browser does not authorize
your terminal client.

### Client examples

Each example reads the token from the `LICTORY_TOKEN` environment variable or
asks for it, so it never lands in a file you might commit. Replace
`lictory.example.com` with your installation's host. Client formats change;
if one of these no longer matches, follow the client's own documentation with
the settings above.

**Claude Code**

```sh
claude mcp add --transport http lictory https://lictory.example.com/api/mcp \
  --header "Authorization: Bearer $LICTORY_TOKEN"
claude mcp list   # lictory should be listed as connected
```

**Codex CLI** (`~/.codex/config.toml`)

```toml
[mcp_servers.lictory]
url = "https://lictory.example.com/api/mcp"
bearer_token_env_var = "LICTORY_TOKEN"
```

**VS Code** (`.vscode/mcp.json`; the token is asked for once and stored by VS Code)

```json
{
  "servers": {
    "lictory": {
      "type": "http",
      "url": "https://lictory.example.com/api/mcp",
      "headers": { "Authorization": "Bearer ${input:lictory-token}" }
    }
  },
  "inputs": [
    {
      "id": "lictory-token",
      "type": "promptString",
      "description": "Lictory personal token",
      "password": true
    }
  ]
}
```

## A first session

Ask the agent:

> List my Lictory organizations and the projects in the Payments organization.
> Read PAY-142, including its current revision and open discussions. Summarize
> the unresolved decisions with links to their context. Make no changes.

The agent starts with `listOrganizations`, then `getWorkspace` to discover the
project's types, workflow, teams and people. `listWorkItems` and `getWorkItem`
read the work; item references can use a key such as `PAY-142`.
`organizationId` accepts an exact ID or slug returned by `listOrganizations`.

For established behavior, ask it to search product knowledge and cite the exact
revision. Draft discussion is evidence of an open question, not an approved
product decision.

## Find and cite knowledge

Two searches serve different questions:

| Capability               | Answers                                                                                                                                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `searchProductKnowledge` | _What did we agree?_ Recorded decisions, approved and delivered specification revisions and published pages, each with its exact version and kind of evidence. Agreements and decisions outrank published pages   |
| `searchKnowledge`        | _Where is this written?_ Full-text search of published pages, work items, decisions and approved or delivered revisions you can read, with an excerpt and the exact version. A match is not evidence of authority |

The links between work and pages are readable too, always limited to pages
you can read:

| Capability                                                | What it returns                                                                                                                                                                                    |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getWorkItemKnowledge`                                    | An item's [Knowledge](/knowledge/in-work): pages that mention it, pages its revisions cite (with pinned versions), attached pages, the page it was created from, and page updates proposed from it |
| `listPageWork`                                            | The work a page knows about: items it mentions, items citing it or attached to it, items created from it, and the projects, teams and iterations that keep it as context                           |
| `listReferencesTo`                                        | Where an item, a page or a decision is referenced, in pages and in specification revisions                                                                                                         |
| `describePageLinks`                                       | The title, version and section of the passages that refer to work, to show a link in context                                                                                                       |
| `listContextPages`                                        | A project's, team's or iteration's [context pages](/knowledge/context-pages)                                                                                                                       |
| `attachPage`, `detachPage`                                | Attach a page to an item as background, design or runbook, optionally pinned to a version (needs **Change properties**)                                                                            |
| `linkContextPage`, `unlinkContextPage`, `moveContextPage` | Keep a page as context of a project, team or iteration                                                                                                                                             |

An agent can create a work item from a passage of a page (`createWorkItem`
with a `source`) and propose a page update that documents an item's revision
(`proposePageChange` with an `origin`), the same way people do in the app
([knowledge](/knowledge)). Page text is data the agent reads, never
instructions it follows.

## Propose a change for review

With a read/write token, ask:

> Read PAY-142 and its current branch heads. Propose timeout and retry behavior
> on a new branch, including acceptance criteria and a delivery breakdown.
> Open a pull request for the team to inspect. Leave approval and merging to us.

The supported proposal flow is:

```text
read current specification and heads
→ createBranch
→ commitBranch (text and optional proposedChildren)
→ createPullRequest
→ people review the resulting change in Lictory
```

Proposed child work becomes shared work only when the pull request merges.
Protected specifications remain protected. A direct `updateSpecification`
is for an explicitly requested edit to an unprotected draft. Agents cannot
type into the [live draft](/specifications/live-drafts) people are editing
together; what people are writing there stays theirs.

Commands can carry a `mutationId`: reusing it for a retry prevents the same
change from being applied twice. A stale `baseRevisionId` returns a conflict
with the current revision, so the agent must read and reconcile the new state.

## Compare readings of done

QA and the coding agent that will build the work can read the same acceptance
criteria differently. You can find that out while the sentence is still being
written. Each person asks their own agent to post a reading of done as a
discussion on the **Acceptance criteria** section. A reading of done says
what the agent would build and test for each criterion. QA replies with their
reading. Where the readings differ, a person decides: the difference becomes
a blocking discussion, a clearer sentence or a [decision](/specifications/decisions).

The agents run on your own clients and models. This flow does not need
Lictory Intelligence or an AI provider on the Lictory server. Each agent
needs a **Read & write** token, and the item needs a heading for the criteria
(here _Acceptance criteria_).

### 1. The implementer's agent posts its reading

Ask the coding agent that will implement the work:

> Read PAY-142 in Lictory: its current revision and its open discussions.
> Write your reading of done for the "Acceptance criteria" section: for each
> criterion, what you would build and how you would test it, with concrete
> numbers, states and errors. List what the text leaves open and do not fill
> it in. Post it as one non-blocking discussion on the "Acceptance criteria"
> section of the current revision. Start it with "My reading of done
> ([your name]'s agent, revision N)". If my agent already has an open reading
> there, reply to it with what changed instead. Do not change the
> specification, resolve discussions or record decisions.

### 2. QA's agent replies with QA's reading

QA asks their own agent:

> Read PAY-142 in Lictory and the "reading of done" discussions on its
> "Acceptance criteria" section. Write QA's reading of done for the same
> criteria: what you would test and which result passes. Reply to each
> reading, criterion by criterion: where we agree and where we differ.
> Start the reply with "QA's reading of done ([your name]'s agent)". Do not
> resolve anything.

### 3. Raise each difference on its sentence

Where a difference must be settled before anyone builds the work, QA (or
anyone who reads the exchange) marks it blocking. In the browser, select the
sentence and start a blocking discussion. Or ask the agent explicitly:

> For each criterion where the two readings of PAY-142 differ, start a
> blocking discussion on that sentence. Quote the words exactly as they read
> in Lictory, without Markdown markers. State both readings in one line each
> and ask which one is done.

A blocking discussion fails the readiness check _No blocking discussion is
open_, so the item cannot become [ready](/review/readiness) until a person
resolves it. Differences that need no decision before building can stay
replies in the reading's discussion.

### What a disagreement looks like

The reading, a non-blocking discussion _on “Acceptance criteria”_ by Devi:

> **My reading of done** (Devi's agent, revision 1).
>
> 1. _Retried up to three times_: the original attempt plus 3 retries, so
>    at most 4 provider calls. A temporary error is a provider 429 or 503,
>    or a network timeout.
> 2. _Pending state_: "Payment pending" from the first failure until the last
>    retry finishes. The customer sees it when they reload.
> 3. _Marked failed and notified_: one email after the last retry fails.
> 4. _Never charged twice_: every retry sends the original transaction ID as
>    the idempotency key.
>
> The text does not say, so I assumed nothing about the total time the
> retries may take or about cancelling while a retry is pending.

Quinn's reply:

> **QA's reading of done** (Quinn's agent, revision 1). Agree on 2 and 4.
> **Differs on 1**: I read "retried up to three times" as three attempts in
> total, so my test would fail the reading above. **Differs on 3**: "the
> customer is notified" means the email and the notice on the order page.

The blocking discussion that follows, on the quoted words _retried up to
three times_:

> Engineering's agent reads this as 1 attempt + 3 retries (4 provider calls);
> QA reads it as 3 attempts in total. Which one is done? Please say the
> number of provider calls in the sentence.

The product owner rewrites the criterion as _retried at most three times
after the first attempt: four provider calls in total_. That saves revision
2, and the blocking discussion now says _The quoted text changed since
revision 1_. Then they choose **Resolve as decision** and record _A retried
charge makes at most four provider calls_. Point 3 stays open in the
reading's discussion until someone settles it.

### What the agents call

| Step               | Tool            | Inputs that matter                                                                                                                                     |
| ------------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Read the item      | `getWorkItem`   | `key` (`PAY-142`). Returns the item's `id`, `specification.revisionId` and Markdown, its `threads` with their anchors and messages, and its readiness  |
| Post a reading     | `createThread`  | `workItemId` (the item's `id`, not its key), `baseRevisionId` (the current revision), `section: "Acceptance criteria"`, `blocking: false`, `body`      |
| Reply              | `replyToThread` | `workItemId`, `threadId`, `body`                                                                                                                       |
| Raise a difference | `createThread`  | As above, with `quote` (the exact words), `blocking: true` and, when those words occur more than once under the heading, `occurrence` (0 is the first) |

`section` is the heading's text without the `#` marks. It matches regardless of
case and formatting, and an unknown heading is refused (_The section “…” is
not in this text._). A discussion anchored to a section without a quote is
listed under **On the whole specification**, labelled with its section. A
quoted one is marked in the text. Lictory does not check the quote when the
discussion is created: words that are not in the text, or that carry
Markdown markers such as `**`, show at once as _The quoted text changed_.
Every call also takes `organizationId`. Pass a `mutationId` so a retried call
does not post twice.

### Decisions stay with people

- **Readings are not approvals.** Two readings that agree approve nothing,
  and no reading makes the item ready. Approvals still belong to the
  reviewers and the revision they reviewed.
- **People resolve discussions and record decisions.** Resolve, Mark
  blocking or non-blocking, and Resolve as decision are human decisions in
  the [discussion panel](/specifications/discussions). A decision can cite a
  discussion only once someone has resolved it.
- **The guardrail is an instruction, not a lock.** The MCP server tells agents
  not to resolve discussions or record decisions unless you ask, but a
  read/write token can call those tools. Use a read-only token for an agent
  that should only read.
- **Say who wrote it.** The activity shows the agent that started a
  discussion (_via devi-terminal (MCP)_). A reply appears under your name
  only, which is why the prompts start each message with whose agent wrote
  it.
- **A reading belongs to its revision.** When the criteria change, ask the
  agents again. An earlier reading still names the revision it read.

## Spaces

Agents read and change [spaces and pages](/spaces) with your space
access: a space you cannot read does not exist for your agent either.

| Capability                                                 | What it does                                                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `listSpaces`                                               | Spaces you can read with your access level, home, access mode and publishing policy                            |
| `listPages`                                                | One space's page tree in reading order                                                                         |
| `getPage`                                                  | A page's published title and Markdown, or any earlier version with `commitId`; never an unpublished live draft |
| `listPageCommits`, `diffPageCommits`                       | A page's history and live branches; what changed between two versions                                          |
| `previewPageMerge`                                         | A page pull request's (or a branch update's) merge as it would happen now, with any conflicts                  |
| `listPageThreads`, `createPageThread`, `replyToPageThread` | Read a page's discussions; start one on the page or a quoted range, and reply                                  |
| `proposePageChange`                                        | A new version of a page from Markdown, on a new branch with an open pull request: the way agents change pages  |
| `createSpace`, `createPage`, `movePage`, `archivePage`     | Organize spaces and the page tree, as your access allows                                                       |

Ask, for example:

> Read the refund runbook in the Payments space and PAY-142's current
> specification. Propose an updated runbook that matches the new timeout
> behavior, and open a pull request for the team. Do not merge it.

Agents cannot type into live drafts, so unpublished edits that people are
making stay theirs. Branches, pull requests, review requests and conflict
resolution (`createPageBranch`, `createPagePullRequest`, `requestPageReview`,
`syncPageBranch`) are available as well, and space administrators can change
access (`setSpaceAccessMode`, `setSpaceGrant`; recorded in the audit log). Publishing a live draft
(`commitDraft`), deciding reviews (`decidePagePullRequest`), merging
(`mergePagePullRequest`) and resolving, reopening or marking discussions
blocking are human decisions, as below; nobody can approve a page change
they contributed to, and that includes an agent acting for them.

## Permissions and human decisions

An agent acts as the person who created its token. Project disciplines determine
work item permissions; organization or project administrator roles do not grant
them. Space access (view, comment or edit) determines what it can do in Spaces. A read-only token exposes queries only. Changing memberships or revoking
the token takes effect on subsequent requests.

Approving reviews, merging, accepting delivery scope, resolving discussions,
recording decisions, signing off readiness checks, publishing the Definition
of Ready and handing work to Jira record human decisions. In projects
delivered in Lictory, an agent cannot start or complete a specification's
work before someone has accepted a revision for delivery. The MCP
tools instruct the agent to perform them only when you explicitly ask. A
read/write token is **not** a technical confirmation gate for each decision:
use read-only access when the agent should only inspect work. Several agents
using one person's identity do not count as independent reviewers.

Account security, organization membership, administrator roles, token
creation, integration credentials, the audit log, data exports, organization
deletion and Litto conversations stay with you in the browser. The agent can call
`listHumanOnlyOperations` to explain where to complete an unavailable operation.

## Audit and disconnect

Activity attributes changes to the person and named agent. Organization
administrators can inspect agent calls and their outcomes in the
[audit log](/organization/audit) (**Agent calls**). Token settings show
expiry and last use. Choose **Revoke** beside a token to
disconnect its agent immediately; create a new token to reconnect.

Connecting a model client gives that client access to the content it reads.
Apply your organization's policy for sending product data to that provider.

## Troubleshooting

| Symptom                    | What to check                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Unauthorized               | Send the bearer header; replace an expired or revoked token.                                                        |
| No tools that make changes | The token is read-only; create a read/write token if needed.                                                        |
| Forbidden operation        | Check current organization membership, project disciplines and the human-only explanation.                          |
| Organization not found     | Rediscover with `listOrganizations`; use its exact ID or slug.                                                      |
| Revision conflict          | Read the latest item and branch heads, then reconcile before retrying.                                              |
| Client cannot connect      | Use `/api/mcp`, remote Streamable HTTP and a reachable HTTPS address; check your reverse proxy and custom CA trust. |

For server diagnostics, use `lictory doctor` and `lictory logs api` on the
installation's host. See [reverse proxies](/self-hosting/reverse-proxy) if
another gateway sits in front of Lictory.
