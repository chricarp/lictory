Settings live in the environment's `.env` file, by default
`/srv/lictory/production/.env` (mode `0600`, owned by the deploy user). Empty
values count as unset. Images carry no domain or analytics settings: the
same image runs on any host name and reads everything here at runtime.

Change settings with `lictory config`. It shows what changes (secrets
masked), keeps a copy of the previous file, and restarts the services with
the new values. If they do not start, it puts the previous settings back:

```sh
sudo lictory config show
sudo lictory config set SMTP_HOST=smtp.example.com SMTP_PORT=587
sudo lictory config edit
```

It refuses a key the release does not read (a typo would otherwise be
ignored silently) and generated secrets such as database passwords and
`DELIVERY_CREDENTIALS_KEY`, whose change breaks the installation. If you edit
`.env` by hand, apply it with `sudo lictory config apply`.

## Domain and TLS

| Setting                | Meaning                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| `APP_HOST`             | The host Lictory is served on, such as `lictory.example.com`                                 |
| `ACME_EMAIL`           | Contact address for certificate issuance                                                     |
| `SITE_HOST`            | Your public website, where the logo links (optional; without it, the app itself)             |
| `PLATFORM_URL`         | The origin users open, when it is not `https://APP_HOST` (another proxy, port or plain HTTP) |
| `CADDY_GLOBAL_OPTIONS` | Gateway options, for example an internal ACME CA (`acme_ca https://…`) or `local_certs`      |

By default the gateway obtains and renews certificates from Let's Encrypt.
`PLATFORM_URL` must be an origin: lowercase, no path, no trailing slash. To
use an internal CA, existing certificate files or a reverse proxy in front,
see [reverse proxy and TLS](/self-hosting/reverse-proxy).

## Email

Lictory sends verification, password reset, invitation and notification
email through **Resend** when `RESEND_API_KEY` is set, otherwise through your
**SMTP** server.

| Setting                               | Meaning                                                  |
| ------------------------------------- | -------------------------------------------------------- |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Resend, with the sender address                          |
| `SMTP_HOST`, `SMTP_PORT`              | Your SMTP server: 587 (STARTTLS), 465 (TLS) or 25        |
| `SMTP_SECURE`                         | TLS from the first byte; `true` by default on port 465   |
| `SMTP_REQUIRE_TLS`                    | `true` refuses to send unless STARTTLS succeeds          |
| `SMTP_USER`, `SMTP_PASSWORD`          | Credentials, when the server requires them               |
| `SMTP_FROM`                           | Sender address, such as `Lictory <no-reply@example.com>` |

A transport needs its sender: a partial setting stops the API and worker with
the problem listed. Without any transport they start, log a warning, and send
no email, so password sign-up cannot be completed (single sign-on still works).

## File storage

Attachments are optional. Without a bucket, the editor offers no upload and
explains that attachments are unavailable. Configure **one** of two sets,
never both: any S3-compatible service (AWS S3, MinIO, Garage, Ceph, Hetzner…)
or the Cloudflare R2 preset.

| S3-compatible                 | Cloudflare R2                                     |
| ----------------------------- | ------------------------------------------------- |
| `S3_ENDPOINT` (empty for AWS) | `R2_ACCOUNT_ID`                                   |
| `S3_REGION`                   | `R2_ACCESS_KEY_ID`                                |
| `S3_BUCKET`                   | `R2_SECRET_ACCESS_KEY`                            |
| `S3_ACCESS_KEY_ID`            | `R2_BUCKET_NAME`                                  |
| `S3_SECRET_ACCESS_KEY`        | `R2_S3_ENDPOINT` (optional jurisdiction endpoint) |
| `S3_FORCE_PATH_STYLE`         |                                                   |

Keep the bucket private and use credentials scoped to it. Browsers upload and
download directly with signed URLs, so the endpoint must be reachable from
users' browsers, and the bucket needs a CORS rule allowing `PUT` from your
`PLATFORM_URL`:

```json
[
  {
    "AllowedOrigins": ["https://lictory.example.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["Content-Type", "Content-Length", "If-None-Match"],
    "MaxAgeSeconds": 300
  }
]
```

A partial or contradictory configuration stops the API at start-up with the
names of the settings to fix.

## Access policy

Nobody can create an account or an organization on their own unless you
allow it. Instance administrators always can, in the admin console
(`https://<your host>/admin`) or with `lictory admin` on the server.
`lictory install` asks for these settings (`--signup-mode`,
`--allowed-email-domains`, `--organization-creation`).

| Setting                         | Meaning                                                                                                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LICTORY_SIGNUP_MODE`           | `invite` (default): a new account needs a pending invitation. `closed`: only instance administrators create accounts. `open`: anyone who can reach the server |
| `LICTORY_ALLOWED_EMAIL_DOMAINS` | Comma-separated email domains for self-service accounts, single sign-on included (empty: any)                                                                 |
| `LICTORY_ORGANIZATION_CREATION` | `administrators` (default) or `everyone`                                                                                                                      |

The rules hold for password sign-up, Google and Microsoft alike, and the
server enforces them. Your company identity provider is the directory: with
`OIDC_AUTO_CREATE_USERS` it creates accounts for the people it admits in
every mode, limited to the allowed domains.

Instance administration is separate from organization roles: instance
administrators manage accounts, organizations and other instance
administrators; organization owners and admins manage their own organization.
From the server, `sudo lictory admin grant <email>` appoints one and
`sudo lictory admin set-password <email>` recovers a lost password.

## Sign-in and single sign-on

Password sign-in works out of the box. Each additional provider appears on
the sign-in page once it is configured:

- **Google**: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, redirect URI
  `https://<your host>/api/auth/callback/google`.
- **Microsoft**: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and
  optionally `MICROSOFT_TENANT_ID` (default `common`), redirect URI
  `https://<your host>/api/auth/callback/microsoft`.
- **Company single sign-on** over OpenID Connect (Okta, Microsoft Entra ID,
  Keycloak, Authentik, Google Workspace, Dex…):

| Setting                  | Meaning                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `OIDC_ISSUER`            | Issuer URL; Lictory reads its `/.well-known/openid-configuration` (HTTPS)                   |
| `OIDC_CLIENT_ID`         | Client ID registered at the provider                                                        |
| `OIDC_CLIENT_SECRET`     | Its secret                                                                                  |
| `OIDC_SCOPES`            | Extra scopes (default `profile`; `openid` and `email` are always requested)                 |
| `OIDC_DISPLAY_NAME`      | Button label, for example `Acme SSO` (default `SSO`)                                        |
| `OIDC_AUTO_CREATE_USERS` | `true` (default) creates an account on first sign-in; `false` admits only existing accounts |
| `PASSWORD_LOGIN_ENABLED` | `false` makes the installation SSO-only                                                     |

Register the redirect URI `https://<your host>/api/auth/callback/oidc` at
the provider. Single sign-on decides who can authenticate; it grants nothing
inside Lictory. Organization membership still comes from invitations, and
an existing account is linked automatically only when the provider asserts
`email_verified`. Provider-specific steps are in the
[single sign-on runbook](https://github.com/chricarp/lictory/blob/main/docs/operations/sso.md).

## Lictory Intelligence

| Setting                       | Meaning                                  |
| ----------------------------- | ---------------------------------------- |
| `OPENAI_API_KEY`              | Enables Lictory Intelligence with OpenAI |
| `LICTORY_AI_MODEL`            | Model for reviews and chat (optional)    |
| `LICTORY_TRANSCRIPTION_MODEL` | Model for dictation (optional)           |

With a key configured, an organization administrator still decides whether
Lictory Intelligence may run for their organization (**Organization settings
→ Lictory Intelligence**). Content people ask it to analyze is sent to
OpenAI; uploaded documents are converted to text on your server first.

## Legal notices

| Setting             | Meaning                                         |
| ------------------- | ----------------------------------------------- |
| `LEGAL_TERMS_URL`   | Your terms of service (an absolute `https` URL) |
| `LEGAL_PRIVACY_URL` | Your privacy notice (an absolute `https` URL)   |

As the operator of your installation, you are responsible for its terms and
privacy notice; Lictory ships none. With either setting, the sign-up and
sign-in pages tell people that creating an account accepts your terms or
acknowledges your notice, and the consent banner links to your notice.
Without them, the app shows no acceptance notice and no legal links: it
never points your users to another operator's terms.

## Analytics

Product analytics are **off** by default: without `POSTHOG_PROJECT_TOKEN`
and `POSTHOG_HOST`, the application loads no analytics code and shows no
consent banner. When you set both, browsers reach PostHog only through your
own `/relay` route, and `ANALYTICS_CONSENT` chooses how analytics follow
each visitor's choice:

- unset: PostHog loads before a choice in cookieless, anonymous mode and
  switches to full tracking after consent; server events are sent regardless
  of the browser choice;
- `strict`: nothing loads until the visitor grants analytics consent, and
  server events are sent only for requests from a browser that granted it.

Which mode you need depends on your own privacy policy.
