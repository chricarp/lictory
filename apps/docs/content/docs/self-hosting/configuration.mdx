Settings live in the environment's `.env` file, by default
`/srv/lictory/production/.env` (mode `0600`, owned by the deploy user). Empty
values count as unset. Images carry no domain or analytics settings; they
read everything here at runtime.

Change settings with `lictory config`. It shows the change (secrets masked),
keeps a copy of the previous file and restarts the services; if they do not
start, it restores the previous settings:

```sh
sudo lictory config show
sudo lictory config set SMTP_HOST=smtp.example.com SMTP_PORT=587
sudo lictory config edit
```

It refuses keys the release does not read (typos) and generated secrets such
as database passwords and `DELIVERY_CREDENTIALS_KEY`, whose change breaks the
installation. Apply a hand edit of `.env` with `sudo lictory config apply`.

## Rotate a secret

Replace a leaked generated secret (a copy of `.env` in the wrong place, a
departing administrator) with a new random one:

```sh
sudo lictory config rotate LICTORY_APP_PASSWORD
```

For a database password, PostgreSQL restarts and applies the new value to
its role before the services restart: expect about a minute of errors. If
PostgreSQL does not take it, the previous value stays.
`BETTER_AUTH_SECRET` signs everyone out (and needs `DELIVERY_CREDENTIALS_KEY`
set first). `DELIVERY_CREDENTIALS_KEY` cannot be rotated yet: stored Jira and Slack
tokens would need re-encrypting.

On an [external database](/self-hosting/database), `rotate` does not change
role passwords (Lictory holds no administrator connection). Set the new value
without applying it, let `database setup` change the role, then apply:

```sh
sudo lictory config set --force --no-apply LICTORY_APP_PASSWORD=$(openssl rand -hex 32)
sudo lictory database setup
sudo lictory config apply
```

## Domain and TLS

| Setting                | Meaning                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| `APP_HOST`             | The host Lictory is served on, such as `lictory.example.com`                                 |
| `ACME_EMAIL`           | Contact address for certificate issuance                                                     |
| `SITE_HOST`            | Your public website, where the logo links (optional; without it, the app itself)             |
| `PLATFORM_URL`         | The origin users open, when it is not `https://APP_HOST` (another proxy, port or plain HTTP) |
| `CADDY_GLOBAL_OPTIONS` | Gateway options, for example an internal ACME CA (`acme_ca https://…`) or `local_certs`      |

The gateway obtains and renews certificates from Let's Encrypt by default.
`PLATFORM_URL` must be an origin: lowercase, no path, no trailing slash. For
an internal CA, existing certificate files or a reverse proxy in front, see
[reverse proxy and TLS](/self-hosting/reverse-proxy).

## Email

Lictory sends verification, password reset, invitation and notification
email through **Resend** when `RESEND_API_KEY` is set, otherwise through your
**SMTP** server.

| Setting                               | Meaning                                                  |
| ------------------------------------- | -------------------------------------------------------- |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Resend, with the sender address                          |
| `SMTP_HOST`, `SMTP_PORT`              | Your SMTP server: 587 (STARTTLS), 465 (TLS) or 25        |
| `SMTP_SECURE`                         | TLS from the first byte; `true` by default on port 465   |
| `SMTP_REQUIRE_TLS`                    | `true` refuses to send unless STARTTLS succeeds          |
| `SMTP_USER`, `SMTP_PASSWORD`          | Credentials, when the server requires them               |
| `SMTP_FROM`                           | Sender address, such as `Lictory <no-reply@example.com>` |

A transport needs its sender: a partial setting stops the API and worker with
the problem listed. Without any transport they start, log a warning and send
no email, so password sign-up cannot complete (single sign-on still works).

## File storage

Attachments are off until you configure a bucket (`lictory install` defaults
to `--storage none`); Lictory keeps no files on the server's disk. Without a
bucket the editors offer no upload, and say who can turn attachments on and
that people can link to files meanwhile. To turn them on, set the variables
below with `lictory config set`. Configure **one** of two sets, never both:
any S3-compatible service (AWS S3, MinIO, Garage, Ceph, Hetzner…) or the
Cloudflare R2 preset.

| S3-compatible                 | Cloudflare R2                                     |
| ----------------------------- | ------------------------------------------------- |
| `S3_ENDPOINT` (empty for AWS) | `R2_ACCOUNT_ID`                                   |
| `S3_REGION`                   | `R2_ACCESS_KEY_ID`                                |
| `S3_BUCKET`                   | `R2_SECRET_ACCESS_KEY`                            |
| `S3_ACCESS_KEY_ID`            | `R2_BUCKET_NAME`                                  |
| `S3_SECRET_ACCESS_KEY`        | `R2_S3_ENDPOINT` (optional jurisdiction endpoint) |
| `S3_FORCE_PATH_STYLE`         |                                                   |

Keep the bucket private, with credentials scoped to it. Browsers upload and
download directly with signed URLs, so the endpoint must be reachable from
them, and the bucket needs a CORS rule allowing `PUT` from your
`PLATFORM_URL`:

```json
[
  {
    "AllowedOrigins": ["https://lictory.example.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["Content-Type", "Content-Length", "If-None-Match"],
    "MaxAgeSeconds": 300
  }
]
```

A partial or contradictory configuration stops the API at start-up with the
names of the settings to fix.

## Access policy

Nobody creates an account or an organization on their own unless you allow
it. Instance administrators always can, in the admin console
(`https://<your host>/admin`) or with `lictory admin` on the server.
`lictory install` asks for these settings (`--signup-mode`,
`--allowed-email-domains`, `--organization-creation`).

| Setting                                    | Meaning                                                                                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LICTORY_SIGNUP_MODE`                      | `invite` (default): a new account needs a pending invitation. `closed`: only instance administrators create accounts. `open`: anyone who can reach the server |
| `LICTORY_ALLOWED_EMAIL_DOMAINS`            | Comma-separated email domains for self-service accounts, single sign-on included (empty: any)                                                                 |
| `LICTORY_ORGANIZATION_CREATION`            | `administrators` (default) or `everyone`                                                                                                                      |
| `LICTORY_ORGANIZATION_DELETION_GRACE_DAYS` | Days between an owner scheduling an organization's deletion and the deletion (1 to 365, default 30). Applies to deletions scheduled after the change          |

The rules apply to password sign-up, Google and Microsoft alike. Your company
identity provider is the directory: with `OIDC_AUTO_CREATE_USERS` it creates
accounts for the people it admits in every mode, limited to the allowed
domains.

Instance administrators manage accounts, organizations and other instance
administrators; organization owners and admins manage their own organization
([instance administration](/organization/instance)). From the server,
`sudo lictory admin grant <email>` appoints one and
`sudo lictory admin set-password <email>` recovers a lost password.

## Sign-in and single sign-on

Password sign-in works out of the box. Each provider below appears on the
sign-in page once configured:

- **Google**: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, redirect URI
  `https://<your host>/api/auth/callback/google`.
- **Microsoft**: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and
  optionally `MICROSOFT_TENANT_ID` (default `common`), redirect URI
  `https://<your host>/api/auth/callback/microsoft`.
- **Company single sign-on** over OpenID Connect (Okta, Microsoft Entra ID,
  Keycloak, Authentik, Google Workspace, Dex…):

| Setting                  | Meaning                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `OIDC_ISSUER`            | Issuer URL; Lictory reads its `/.well-known/openid-configuration` (HTTPS)                   |
| `OIDC_CLIENT_ID`         | Client ID registered at the provider                                                        |
| `OIDC_CLIENT_SECRET`     | Its secret                                                                                  |
| `OIDC_SCOPES`            | Extra scopes (default `profile`; `openid` and `email` are always requested)                 |
| `OIDC_DISPLAY_NAME`      | Button label, for example `Acme SSO` (default `SSO`)                                        |
| `OIDC_AUTO_CREATE_USERS` | `true` (default) creates an account on first sign-in; `false` admits only existing accounts |
| `PASSWORD_LOGIN_ENABLED` | `false` makes the installation SSO-only                                                     |

Set Google or Microsoft sign-in with `lictory config` (company single sign-on
is also an installer step, `--oidc yes`):

```sh
sudo lictory config set GOOGLE_CLIENT_ID=… GOOGLE_CLIENT_SECRET=…
```

Register the redirect URI `https://<your host>/api/auth/callback/oidc` at
the provider. Single sign-on decides who can authenticate and grants nothing
inside Lictory: organization membership comes from invitations, and an
existing account is linked automatically only when the provider asserts
`email_verified`. Provider-specific steps:
[single sign-on runbook](https://github.com/chricarp/lictory/blob/main/docs/operations/sso.md).

## Lictory Intelligence

Set up AI providers in the admin console (**Admin console → AI providers**)
or in the terminal:

```sh
sudo lictory ai setup     # choose providers, models and keys; test; save
sudo lictory ai check     # check what is saved
```

Supported: cloud providers (OpenAI, Anthropic, Google Gemini and Vertex AI,
Azure OpenAI, Amazon Bedrock, Mistral, xAI, Groq, DeepSeek, OpenRouter) and
open-weight models on your own hardware (Ollama, vLLM, LM Studio, llama.cpp,
Whisper servers for dictation). [AI providers](/self-hosting/ai-providers)
covers each one, self-hosted models, dictation and the environment variables
(`LICTORY_AI_*`), which take precedence when set.

An organization administrator still decides whether Lictory Intelligence runs
for their organization (**Organization settings → Lictory Intelligence**).
Content people ask it to analyze is sent to the configured provider; uploaded
documents are converted to text on your server first.

## Live editing

Live editing of [pages in Spaces](/spaces/editing) and
[specification drafts](/specifications/live-drafts) needs no setup: the
`collaboration` service shares the database, sign-in and address, and the
gateway routes `/collaboration` to it. Behind your own proxy, pass that
path's WebSocket upgrades ([reverse proxy and TLS](/self-hosting/reverse-proxy)).

| Setting                   | Meaning                                                    |
| ------------------------- | ---------------------------------------------------------- |
| `COLLABORATION_MEM_LIMIT` | Memory limit of the collaboration service (default `384m`) |
| `COLLABORATION_HEAP_MB`   | Its JavaScript heap, below the limit (default `256`)       |

Run exactly one collaboration service per database (editors must share one
to see each other); a second copy refuses to start.

## Legal notices

| Setting             | Meaning                                         |
| ------------------- | ----------------------------------------------- |
| `LEGAL_TERMS_URL`   | Your terms of service (an absolute `https` URL) |
| `LEGAL_PRIVACY_URL` | Your privacy notice (an absolute `https` URL)   |

As the operator, you are responsible for your installation's terms and
privacy notice; Lictory ships none. With either setting, the sign-up and
sign-in pages say that creating an account accepts your terms or acknowledges
your notice, and the consent banner links to your notice. Without them, the
app shows no acceptance notice and no legal links.

## Analytics

Product analytics are **off** by default: without `POSTHOG_PROJECT_TOKEN`
and `POSTHOG_HOST`, no analytics code loads and no consent banner shows. With
both set, browsers reach PostHog only through your own `/relay` route, and
`ANALYTICS_CONSENT` sets how analytics follow each visitor's choice:

- unset: PostHog loads before a choice in cookieless, anonymous mode and
  switches to full tracking after consent; server events are sent regardless
  of the browser choice;
- `strict`: nothing loads until the visitor grants analytics consent, and
  server events are sent only for requests from a browser that granted it.

Which mode you need depends on your privacy policy.
