## Health endpoints

| Check                    | Where                                                                 |
| ------------------------ | --------------------------------------------------------------------- |
| API liveness / readiness | `GET /healthz`, `GET /readyz` on your Lictory host                    |
| zero-cache               | `GET /keepalive`, inside the internal network                         |
| Collaboration            | `GET /livez`, `GET /readyz` on port 3004, inside the internal network |
| Worker, proxy            | Container health checks                                               |

Point any uptime checker or load balancer at `https://<your host>/readyz`.

## Built-in monitor

Every five minutes the monitor checks, and alerts on:

- the public `/readyz` route;
- disk usage above 80 %;
- unhealthy or stopped containers, the collaboration service included;
- a lagging, lost or orphaned replication slot, and `pg_wal` above 6 GB;
- failed or stuck AI runs, failed or overdue notification email, and
  partial, failed or stuck Jira exports;
- automatic cycles overdue by two hours;
- a backup older than 30 hours (unless backups are disabled).

It posts to `ALERT_WEBHOOK_URL` (Slack- and Discord-compatible JSON) when the
set of problems changes, every six hours while they persist, and once on
recovery. It also pings `MONITOR_PING_URL` (or `<url>/fail`), so an external
dead-man's switch notices a server that stopped reporting. Both are optional.
In-server checks cannot report a total outage: keep one external check.

To feed `lictory doctor`'s checks into your own monitoring, use its JSON
form. It exits 1 when a check fails, like the text form:

```sh
lictory doctor --json | jq '.checks[] | select(.status != "ok")'
```

The monitor does not install releases. To hear about a new one, schedule
`lictory upgrade --check`, which exits 10 when the channel has a newer
release:

```sh
# /etc/cron.d/lictory-release-check: weekdays at 08:00, posts to the alert webhook
0 8 * * 1-5 root lictory upgrade --check >/dev/null; [ $? -ne 10 ] || curl -fsS -H 'Content-Type: application/json' -d '{"text":"A new Lictory release is available: sudo lictory upgrade"}' "$(lictory config get ALERT_WEBHOOK_URL)"
```

## Existing monitoring

Scrape container health with cAdvisor or the Docker engine metrics endpoint,
and use `postgres_exporter` for replication slot lag and WAL size (the
queries are in
[`deploy/monitor/checks.sql`](https://github.com/chricarp/lictory/blob/main/deploy/monitor/checks.sql)).
Container logs rotate at 5 × 20 MB.
