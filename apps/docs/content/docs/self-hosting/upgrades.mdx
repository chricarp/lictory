## Release channels

Lictory publishes two channels as [GitHub Releases](https://github.com/chricarp/lictory/releases):

| Channel     | Version                        | For                                                          |
| ----------- | ------------------------------ | ------------------------------------------------------------ |
| **Stable**  | `X.Y.Z`                        | Production. Promotes the exact commit of a tested nightly    |
| **Nightly** | `X.Y.Z-nightly.YYYYMMDD.<run>` | Staging and testing. Built daily from `main` when it changed |

Versions follow semantic versioning: features raise the minor version,
fixes the patch version, and breaking changes the major version (the minor
version while Lictory is `0.x`). Each release's notes list breaking changes
first, with any upgrade action. An installation accepts only releases of its
configured channel (`LICTORY_RELEASE_CHANNEL`: `stable` or `nightly`).

Nightly releases are kept for 14 days once a newer nightly exists; the
newest nightly is always available, however old. Stable releases are never
removed. To stay on a specific nightly for longer, keep it installed: a
removed nightly can no longer be installed by version, but an installation
that runs it is unaffected.

## Verify release images

Lictory's images are signed by the GitHub Actions workflow that published
them, so you can check that what you install is exactly what the project
released, before you install it or approve an upgrade. Each release has:

- a **cosign signature** (Sigstore keyless) and a **GitHub artifact
  attestation** (SLSA build provenance) for every image digest;
- an **SBOM** (SPDX) and full build provenance inside every image;
- the SBOMs (`lictory-api-linux-amd64.spdx.json` and so on) and a
  **third-party license report** (`third-party-licenses.json`,
  `THIRD_PARTY_NOTICES.txt`) attached to its GitHub Release.

The images to check are the digests in the release's `release.env` (on a
server, `/srv/lictory/production/current/release.env` is the active one).
Set the release and the workflow that published it:

```sh
version=0.25.0
workflow=release.yml  # nightly.yml for a nightly
ref=refs/heads/main   # refs/heads/release/X.Y for a nightly of a maintenance branch

curl -fsSL -o "lictory-$version.env" \
  "https://github.com/chricarp/lictory/releases/download/v$version/release.env"
images=$(sed -nE 's/^(API|PROXY|MIGRATE|OPS)_IMAGE=//p' "lictory-$version.env")

# With cosign (no GitHub account needed)
(set -e; for image in ${images:?release.env lists no images}; do
  cosign verify "$image" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    --certificate-identity "https://github.com/chricarp/lictory/.github/workflows/$workflow@$ref" \
    >/dev/null
  echo "signed: $image"
done)

# Or with the GitHub CLI (signed in)
(set -e; for image in ${images:?release.env lists no images}; do
  gh attestation verify "oci://$image" --repo chricarp/lictory \
    --signer-workflow "chricarp/lictory/.github/workflows/$workflow" \
    --source-ref "$ref"
done)
```

Each check stops at the first image that fails and exits non-zero unless
every digest was signed by that Lictory workflow on that branch; it also
fails when the release's `release.env` could not be downloaded. To read an
image's SBOM without downloading it:

```sh
docker buildx imagetools inspect "$(sed -n 's/^API_IMAGE=//p' "lictory-$version.env")" \
  --format '{{ json (index .SBOM "linux/amd64").SPDX }}'
```

`lictory` itself does not check signatures; use these commands, or the same
identity in your cluster's admission policy. Releases published before
signing was introduced (0.24.0 and earlier) have no signatures or SBOM
files. The
[release runbook](https://github.com/chricarp/lictory/blob/main/docs/operations/releases.md#signatures-and-attestations)
explains what each signature covers.

## Before you upgrade production

1. **See what is available:** `lictory upgrade --check` names the newest
   release of your channel without changing anything.
2. **Read its release notes.** Breaking changes come first, each with the
   action it needs (a setting to add, a proxy rule to change).
3. **Upgrade staging first**, if you have it, and use it for a day. On a
   server that hosts both, remember that the host tools follow the newest
   release you activate ([multiple environments](/self-hosting/terminal#multiple-environments)).
4. **Know your way back.** Upgrades take a backup themselves when the
   release has migrations, but a recent [restore drill](/self-hosting/backups#restore-drill)
   is what proves you can use it. `lictory backup list` shows what you have.
5. **Pick a quiet moment.** Migrations run while the previous release keeps
   serving (each one is written to work with it), API restarts drop no
   requests, and the proxy restarts for about two seconds (below).

On an installation with a long history of specifications and pages, the
release that links work and pages builds search indexes that pause saving
specifications and committing pages while they build. To avoid the pause,
build them beforehand without blocking anyone, as the
[migration runbook](https://github.com/chricarp/lictory/blob/main/docs/operations/migrations.md#prebuilding-indexes-before-an-upgrade)
describes; the upgrade then skips them.

## Upgrade

<Cli command="upgrade" />

To find out first whether there is anything to install, without changing
anything:

```sh
lictory upgrade --check          # exit 10 when a newer release exists
lictory upgrade --check --json   # {"version", "latest", "upgradeAvailable", …}
```

`lictory doctor` also says when a newer release of the channel is available.

Without a version, the newest release of the channel is installed. An
upgrade runs three steps, and stops before changing anything if the first
fails:

1. **Prepare**: validate the release, pull its images by digest and check
   the gateway configuration.
2. **Migrate**: if the release has migrations, take a backup, apply them,
   and wait until zero-cache has replicated them.
3. **Activate**: replace zero-cache, the proxy, the API, the worker and the
   collaboration service one by one, each waiting for its health check, then
   verify the application, the realtime connection and live editing. If anything fails, the previous release's images
   are restored automatically, and the command says whether the environment
   runs the previous release again and is healthy, or needs attention now
   (`lictory doctor`).

The proxy holds requests for up to 30 seconds while the API is replaced, so
API restarts drop no requests. Replacing the proxy itself refuses connections
for about two seconds; open browser tabs reconnect on their own. Replacing
the collaboration service pauses live editing of pages and specifications for
a few seconds:
saved edits are already stored, and editors' unsaved edits are sent again
when they reconnect.

## One-time maintenance after an upgrade

Some releases need a one-time job after the upgrade, a **backfill**, to bring
existing data up to date. Its release notes say so, with its name.
Backfills run while Lictory keeps serving, can be interrupted and run again
safely, and never rewrite revisions, approvals, decisions or audit history.

Run one with the version you just installed (`lictory status` shows it):

```sh
sudo /srv/lictory/bin/deploy.sh production backfill <version> <name>
```

For example, installations that had pages or specifications before the
release that links work and pages (each work item's **Knowledge**, pages
listing the work they mention, citations of page versions) run
`rebuild-knowledge-index` once. Until then, mentions and citations written
before the upgrade are missing from Knowledge and from the work linked to a
page; new ones are indexed as they are published or saved. The job only
reads pages and revisions and writes the index derived from them; running it
again changes nothing.

```sh
sudo /srv/lictory/bin/deploy.sh production backfill <version> rebuild-knowledge-index
```

Use your environment's name instead of `production`. If it stops with an
error, fix the cause and run it again.

## Roll back

<Cli command="rollback" />

A rollback switches the application images back to the previously activated
release. **Database migrations stay applied**: every migration is written so
that the previous release keeps working against the new schema. Publish or
install a fix as a new release rather than staying on an old one.
