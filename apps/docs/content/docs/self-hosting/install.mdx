## Before you start

1. Provision a server that meets the [requirements](/self-hosting#requirements)
   and harden it to your own standard.
2. Create DNS records for your Lictory host (for example
   `lictory.example.com`) pointing at the server. If certificates come from
   Let's Encrypt, a `CAA` record must allow `letsencrypt.org`. Lower the TTL
   to 300 seconds a day before moving existing traffic.
3. Prepare the settings the installation will ask for: the host name, an
   email address for certificate notices, your email service, and any
   optional integration ([configuration](/self-hosting/configuration)).

## Install

Install the `lictory` command, then run the installer as root:

<Cli command={["bootstrap", "install"]} />

`lictory install` guides you through nine steps: it checks the server
(Docker and Compose versions, memory, disk), asks for the address and checks
DNS and ports, asks where PostgreSQL runs (on the server, or an
[external database](/self-hosting/database)), asks for email, attachment
storage, single sign-on and backups, then for the [access policy](/self-hosting/configuration#access-policy):
who may create accounts and organizations. It shows a review of every
answer, with secrets masked, before it changes anything. On a terminal the
choices are menus (arrow keys and Enter) and long steps show progress while
their output goes to a log under `/srv/lictory/production/logs`.

For an unattended install, pass the settings as flags with `--yes`, or as
`LICTORY_<FLAG>` environment variables to keep secrets out of the shell
history (for example `LICTORY_SMTP_PASSWORD`). The bootstrap installs the
newest stable release; set `LICTORY_CHANNEL=nightly` or
`LICTORY_VERSION=<version>` before it to choose another. It verifies the
release's image digests before pulling anything. Settings and generated
secrets are written to the environment's `.env` file (by default
`/srv/lictory/production/.env`, mode `0600`): database passwords,
`BETTER_AUTH_SECRET`, `DELIVERY_CREDENTIALS_KEY` and the Zero keys are
generated for you.

<Callout type="warn" title="Keep a copy of .env">
  Store the `.env` file in your password manager. Two values matter in a
  recovery: `BETTER_AUTH_SECRET` keeps sessions valid, and
  `DELIVERY_CREDENTIALS_KEY` keeps stored Jira credentials readable. Never
  rotate `DELIVERY_CREDENTIALS_KEY` once Jira is connected.
</Callout>

On an empty database the first release does everything in order: PostgreSQL
creates its roles and databases, the migrations run, zero-cache performs its
initial sync, then the proxy, API and worker start.

Installing from a **private repository or a fork**? GitHub hides private
releases without a token: run the bootstrap in a root shell with
`GITHUB_TOKEN` set to a token that can read the repository (and
`LICTORY_REPOSITORY` and `LICTORY_IMAGE_REGISTRY` for a fork); `lictory
upgrade` needs it too. The
[operator runbook](https://github.com/chricarp/lictory/blob/main/docs/operations/self-hosting.md#bootstrap)
has the exact commands.

For keyboard controls, unattended examples, reconfiguration and account recovery,
see the [terminal guide](/self-hosting/terminal).

## The first administrator

The last step creates the first **instance administrator**, the account that
runs Lictory, and the organization they own: the organization's name and
handle (its address, `https://<your host>/<handle>`), your name, work email
and a password. The email counts as verified, so this works before email is
configured. With `--yes`, pass `--organization`, `--admin-name` and
`--admin-email`, and the password in `LICTORY_ADMIN_PASSWORD`; without them
the step waits for `sudo lictory admin setup`.

<Cli command={["admin-setup", "admin-grant"]} />

Sign in as the administrator and open the admin console at
`https://<your host>/admin`: invite people, create accounts and
organizations, and appoint other administrators. From the server,
`lictory admin` does the same when nobody can sign in, for example to recover
the only administrator:

<Cli command={["admin-create-user", "admin-set-password"]} />

## Check the installation

<Cli command={["status", "doctor"]} />

Then, in a browser:

- sign in as the administrator and open the admin console;
- invite a colleague, accept the invitation in another browser and reset a
  password (this needs outbound email);
- open the same specification in two browsers and check that a change in one
  appears in the other (the realtime connection);
- upload and download an attachment, if file storage is configured;
- run a first [backup](/self-hosting/backups) and a restore drill.
