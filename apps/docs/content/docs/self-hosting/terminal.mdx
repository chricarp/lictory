The `lictory` command installs and operates a self-hosted server. Run it on
the server (SSH or console) as root or the deploy user. For coding agents, see
[AI agents and MCP](/integrations/agents).

## The guided experience

<Cli command={["bootstrap", "install"]} />

The bootstrap installs the command; `install` starts the guided setup:

1. Check Docker, Compose, required tools, memory and disk.
2. Choose the address and certificate mode; check DNS and ports.
3. Configure email, optional attachments and single sign-on, and backups.
4. Choose who can sign up and create organizations.
5. Review the configuration, with secrets masked and changed keys identified.
6. Confirm, write the settings and install the release.
7. Check that the application is ready and start the scheduled jobs.
8. Create the first instance administrator and their organization.

In bash, **Tab** completes commands, options, environment names, services and
setting names (the bootstrap installs `/etc/bash_completion.d/lictory`; for
another shell or user, `lictory completion bash` prints the script).

Select a menu entry with **↑/↓**, **j/k** or its number, then **Enter**. At
text prompts, Enter keeps the displayed default. Passwords are hidden; new
ones are confirmed twice. Invalid answers are explained at the prompt.

Long tasks show elapsed progress and write detailed output to
`/srv/lictory/<env>/logs/install-<timestamp>.log`; if a task fails, the
command shows the log's tail and its path. The final summary gives the
application address, administrator, admin console and remaining tasks.

`NO_COLOR=1` disables styling and uses text prompts. Redirected output and
pipes are plain text. `--yes` disables questions for automation; input from a
pipe is also unattended. CI needs no terminal UI.

## Inspect health and logs

<Cli command={["status", "doctor", "logs"]} />

`status` shows the address, the active release and when it was activated,
each service's health, the backup timer's last and next run, and the access
policy: one panel on a terminal, `key: value` lines when piped, JSON with
`status --json`.

To follow only the background worker:

```sh
lictory logs worker -f --tail 100
lictory logs api --since 2h --timestamps   # everything since an incident began
```

Services: `proxy`, `api`, `worker`, `collaboration` (live editing of pages
and specifications), `zero-cache` and `postgres`. `api`, `worker` and
`collaboration` write one JSON object per line, `time`, `level`, `service`
and `event` first, so a log pipeline can filter by level and order them
without Docker's timestamps. Tooling history is in
`/srv/lictory/<env>/deploy.log` and `release-history.log`, separate from
service and installer logs.

## Ask for help

Start with `lictory doctor`: it names most problems and the command that
fixes them. Otherwise collect a support bundle and open an
[issue](https://github.com/chricarp/lictory/issues/new/choose):

<Cli command="support-bundle" />

The archive (mode `0600`) holds host and Docker versions, status, doctor, the
settings with secrets masked, the containers, deploy history, timers and each
service's logs for the last 24 hours (`--since 72h` for more). Secret values
from `.env`, email addresses and bearer tokens are replaced, but logs can
still contain your organization's content, such as project or specification
titles: paste only the relevant lines into a public issue.

## Reconfigure an installation

Run `sudo lictory install` again. Enter keeps current values; generated
secrets and unchanged settings are kept. The review step lists changed `.env`
keys before applying them. To change one setting without the questions, pass
flags:

```sh
sudo lictory install --yes --signup-mode closed
```

For any other setting, use `lictory config`. It lists the change (secrets
masked), keeps a copy of the previous `.env` and restarts the services,
restoring the previous settings if they do not start:

<Cli command="config" />

```sh
sudo lictory config show            # every setting, secrets masked
sudo lictory config get APP_HOST    # one value, for scripts
sudo lictory config edit            # in $EDITOR, with a review before saving
sudo lictory config apply           # after editing .env by hand
```

A misspelled key or a change to a generated secret (database passwords,
`DELIVERY_CREDENTIALS_KEY`) is refused without `--force`. Every setting:
[configuration](/self-hosting/configuration). Every command's options:
`--help`, for example `lictory install --help`.

## Unattended installation

Pass the answers as flags with `--yes`. For example, on a server whose DNS
and ports are ready for automatic HTTPS:

```sh
sudo lictory install --yes \
  --host lictory.example.com \
  --acme-email ops@example.com \
  --email smtp \
  --smtp-host smtp.example.com \
  --smtp-port 587 \
  --smtp-user lictory \
  --smtp-from 'Lictory <no-reply@example.com>' \
  --signup-mode invite \
  --organization-creation administrators
```

Every install flag also accepts a `LICTORY_<FLAG>` environment variable
(hyphens as underscores). Pass `LICTORY_SMTP_PASSWORD` from your automation's
secret store to the privileged process; `sudo` may drop variables set in your
user shell. Do the same for `LICTORY_ADMIN_PASSWORD` when creating the
administrator unattended with `--organization`, `--admin-name` and
`--admin-email`.

Without administrator details, installation defers account setup. Complete it
afterwards:

<Cli command="admin-setup" />

The bootstrap installs the newest stable release. For nightly, pass the
variable to the shell running the download:

```sh
curl -fsSL https://raw.githubusercontent.com/chricarp/lictory/main/deploy/get.sh \
  | sudo LICTORY_CHANNEL=nightly sh
```

`LICTORY_VERSION` pins an exact bootstrap release. Every option, variable and
exit code: [command reference](/self-hosting/commands).

## Multiple environments

Every command accepts `--env <name>` (or `-e`); with only one environment, it
is found automatically. Name it explicitly in scripts:

```sh
lictory status --env production --json
lictory doctor --env staging
lictory logs api --env staging --tail 50
```

Each environment has its own configuration, database, Docker volumes and
deployment lock. Check the environment before a write such as upgrade,
restore or account administration.

Environments on one server share:

- **Ports.** Only one environment can serve ports 80 and 443 with automatic
  HTTPS. Install the others with `--tls proxy` and a different
  `--http-port` (for example 8081), behind a reverse proxy that routes each
  host name to its port ([reverse proxy and TLS](/self-hosting/reverse-proxy)).
- **Host tooling.** The `lictory` command and the scripts in
  `/srv/lictory/bin` come from the newest release activated on the server, so
  upgrading staging first also updates the tools production uses. They stay
  compatible with older releases; keep a server's environments within one
  release line (`lictory doctor` warns when an environment's release and the
  host tools are on different lines).

## Recover access

Instance administration runs inside the API container, so it works when
nobody can sign in. Create the first administrator with `admin setup`, or
grant instance administration to an existing account:

<Cli command={["admin-grant", "admin-create-user", "admin-set-password"]} />

`admin set-password` signs the account out everywhere. Passwords are read at
the prompt or from `LICTORY_USER_PASSWORD`. `admin deactivate <email>` blocks
sign-in and ends sessions; `admin reactivate <email>` restores access.
`admin revoke <email>` removes instance administration. Deactivation and
revocation ask for confirmation; the last active administrator is protected.

Instance administrators manage accounts and organizations, with no access to
an organization's work. Owning the organization the first setup creates is a
separate authority.

## Upgrade, roll back and test recovery

<Cli command={["backup", "upgrade", "rollback"]} />

Upgrade verifies release digests, backs up, applies migrations and activates
the newer release. Rollback reactivates the previous images; **it does not
undo database migrations**. Read [upgrades](/self-hosting/upgrades) before
switching versions; a [restore drill](/self-hosting/backups#restore-drill)
proves a backup is usable before an incident.

## Stop or remove an environment

<Cli command="uninstall" />

Without `--purge`, the environment stops and its containers and scheduled
jobs are removed; the database, settings and backups stay, and
`sudo lictory config apply` starts it again. `--purge` deletes the database
volumes and the environment's directory, including `.env` and its secrets.
When backups go off the server, a final backup is taken first, and nothing is
deleted if it fails. You type the environment name to confirm. Docker, other
environments, the `lictory` command and the deploy user are never touched;
with no environment left, the command prints how to remove the tooling too.

`lictory help` and `lictory admin help` show usage; the
[self-hosting overview](/self-hosting#operating-the-server) lists the commands.
