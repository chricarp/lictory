### `createWorkItem`

**Create work item.** Command · retry key `mutationId`

Create a work item (Epic, Story, Task, Bug, Subtask or a custom type enabled in the project). Spec-backed types require edit-specifications; plain types require edit-specifications or change-properties in the project. `teamId` is optional. `typeId` and `teamId` come from getWorkspace; `description` is Markdown and becomes the first revision. Unknown fields are rejected. Specification text belongs in `description`, not `content`. Set an estimate afterwards with updateWorkItem. `source` \{ pageId, commitId, blockId?, quote? \} records committed page content the item is created from (you must be able to read the page; the commit must be one of its versions, the block one of that version's top-level blocks, the quote at most 2000 characters); only readers of the page see it. The result includes `key` and `revisionId`.

### `commitBranch`

**Commit to branch.** Command · retry key `mutationId`

Commit a title, Markdown content and optional proposedChildren to a branch. Each entry is a new child (stable workItemId, typeId of an enabled type whose level is below the parent's, such as a Task or Bug under a Story, title, description) or a change to an existing direct child (changeId, workItemId, base \{revisionId, title\} read from the child, then title/description for children without a specification, parentId to move it (null detaches), or archive: true). Entries apply only after reviewed merge into main; a change applies only while the child still has its base revision and is not accepted, underway or handed off. Omit proposedChildren to preserve the base breakdown; supply the complete list when editing it. Entries already accepted in main must stay unchanged. `baseCommitId` identifies the inspected base; concurrent nonoverlapping changes combine and conflicts require explicit resolution.
