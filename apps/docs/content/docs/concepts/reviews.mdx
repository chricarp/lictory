title: Reviews, discussions and approvals
description: How disciplines review a specification, how discussions stay anchored to their context, and why every approval belongs to one revision.

## Reviews

A **review** asks a discipline of the project (Product, Engineering, QA,
Security…) to evaluate the specification, optionally naming one person in
it. The discipline's name is the review responsibility. Only an assigned
person, or a current member of the assigned discipline, can decide the
review: **Approve** or **Request changes**. Holding a discipline never
approves anything by itself.

A review is **required** (it counts for readiness) or **optional** (it
informs). Requesting a review moves a draft or refining specification to _in
review_. A request notifies the reviewers it is assigned to; a decision
notifies the item's owners and whoever requested the review. When the
specification is revised, every active review is requested again on the new
revision with the same assignments. See [request
reviews](/review/requests).

## Discussions

A **thread** is a discussion attached to its context: a quoted passage of the
specification (with the heading it is under), the specification as a whole,
or a pull request. It keeps the revision it was written on. In later
revisions Lictory looks for the quoted text again and says when it changed or
was removed, so nobody has to ask what a comment referred to, and a comment
is never moved to other text.

Threads are **blocking** or **non-blocking**. An open blocking thread on a
specification keeps it from becoming ready (when the project's checks include
it, as they do by default); an open blocking thread on a pull request keeps
that pull request from merging. Resolving and reopening never delete
messages; the activity keeps every step. When a thread reaches an important
conclusion, record it as a [decision](/specifications/decisions). See
[discuss a specification](/specifications/discussions).

## Approvals belong to revisions

An **approval** states that a reviewer accepted one specific revision for
their discipline. It is never a permanent flag on the item:

- A change to the title or text creates a new revision and makes the earlier
  approvals **stale**, recording who caused it, when and why. The reviewers
  are notified and asked again on the new revision; the old decisions stay in
  history.
- The item shows the difference plainly: _Engineering approved revision 12;
  the current revision is 14; Engineering's approval requires review._
- Property changes (status, assignee, iteration, estimate…) are not revisions
  and never affect approvals.

On a pull request, approvals record a fingerprint of the complete result of
the merge, breakdown included. Any change to the source or the target that
alters that result makes them stale; changes that leave it identical keep
them. People who authored commits in a pull request cannot approve it, unless
they are the organization's only member. A pull request merges only when every
required review approves its current result, nobody currently requests
changes, no blocking thread is open and no conflict remains. Merging carries
its valid approvals to the new revision, so the team does not approve the
same text twice. See [approve or request changes](/review/approvals).

## Lictory Intelligence is a check, not an approval

Lictory Intelligence raises findings and questions and can propose changes on
its own branches. A project can require a clean Lictory Intelligence review as
a [readiness check](/review/readiness#lictory-intelligence-check), but it
never counts as a discipline's approval and is always required beside a
person's decision. Anyone holding a discipline can override the check for one
revision. Litto or an MCP agent can record an approval only on a person's
explicit instruction, and the approval is that person's.
