title: Delivery
description: How agreed specifications become delivered work, natively in Lictory or in Jira, with exactly one system owning delivery for each project.
---

Delivery mode is a per-project setting (**Project settings → Delivery**).
Refinement works the same in both modes. For the same piece of work,
exactly one system owns delivery state.

| Native (Deliver in Lictory)                         | External (Hand off to Jira)                 |
| --------------------------------------------------- | ------------------------------------------- |
| Board, backlog, sprints or cycles, estimates        | Jira plans, estimates and tracks the work   |
| Status and assignee are set in Lictory              | Status and assignee are read back from Jira |
| **Accept for delivery** records the agreed revision | Handing off records the agreed revision     |
| The readiness policy gates starting work            | Only ready specifications are handed off    |

## Eligibility and commitment

**Ready for delivery** means the readiness checks pass for the current
revision: the work can be selected. It is not a commitment. **Accept for
delivery** is the accountable decision that the team will build a revision,
and records it. Starting work records it automatically when nobody accepted
yet. Moving to done records the accepted revision as **Delivered**.

A later revision never replaces the agreement silently. The item shows the
difference until someone accepts the new revision (native) or hands it off
(Jira). See [deliver the work](/delivery).

## Delivery items

An approved specification is decomposed into child work items (Stories,
Tasks, Subtasks). Children can be added directly or proposed as a reviewed
breakdown on a branch, approved with the specification and created at
merge. Each child records the revision of the parent it was derived from.
Plain items under a specification follow its readiness, so splitting
unsettled behavior into Tasks does not bypass the gate. See
[break down a specification](/delivery/breakdown).

## Native delivery

- **Types** are an organization-wide registry that projects opt into. A type
  has a hierarchy level (Epic above Story, Task and Bug, above Subtask) and
  says whether it carries a specification. Epics are delivered through their
  children.
- **Workflows** are per project: statuses you name, each in a fixed category
  (`backlog`, `unstarted`, `started`, `done`, `canceled`). Any transition is
  allowed. See [the board](/delivery/board).
- **Iterations** are sprints (by hand) or cycles (automatic). One is active
  per project at a time. See [sprints and cycles](/delivery/iterations).
- **Estimates and reports**: integer estimates, burndown, scope change and
  velocity from recorded events, frozen at completion. See
  [reports](/delivery/reports).
- **Relations**: _blocks_, _relates to_ and _duplicates_, across projects
  and teams. See [relations](/delivery/relations).
- **Teams** narrow boards and backlogs to one group without changing an
  item's identifier, status or iteration. See [teams](/delivery/teams).

## External delivery

Lictory refines, reviews and approves; Jira delivers. The **Hand-off** view
replaces the board. Lictory writes the summary, description and labels;
Jira's status and assignee are read back and shown read-only. Hand-off is
explicit, recorded per item and safe to retry. See
[Deliver in Jira](/integrations/jira).
