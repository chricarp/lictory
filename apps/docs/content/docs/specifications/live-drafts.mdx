---
title: Edit a specification together
description: Co-edit a specification's live draft with your team, see who is writing, and save the result as a revision only when it is ready.
---

Several people can edit the same specification at once. Each line of a
specification (the specification itself, or one
[proposed change](/specifications/branches)) has one shared **live draft**:
everyone editing sees the others' named carets, and edits save as they are
typed.

A live draft is a working copy, never history. Only **Save revision** (on the
specification) or **Save version** (on a proposed change) turns it into an
immutable revision or version. Review starts from there: approvals belong to
revisions, discussions are written on revisions, readiness reads the current
revision.

## When to use it

- A product owner and an engineer working through the expected behavior
  together, on a call or not.
- QA adding failure cases while Product is still writing the outcome.
- Anyone fixing a sentence while others are in the document.

No need to coordinate: edits merge character by character, and nobody
overwrites anyone else.

## Edit main

<Steps>
<Step>

### Open the editor

On the specification, choose **Edit**. If the shared draft holds edits
nobody saved, **Draft not saved as a revision** appears next to **Edit** and
opens the editor with them.

</Step>
<Step>

### Write

The line above the text shows:

- **Live draft · based on revision N**: the revision the draft started
  from.
- The **save state** of the draft (see [below](#draft-saved-is-not-a-revision)).
- **Not saved as a revision yet** when the draft holds edits no revision
  has, or **Same as revision N** when it does not.
- Who else is editing, for example _Dev Patel is editing_.

![Maria Chen and Dev Patel editing the PAY-3 specification at the same time: Dev Patel’s named caret in the Behavior section, the status line “Live draft · based on revision 2 · Draft saved · Not saved as a revision yet” with Dev Patel is editing, and Close editor and Save revision 3](/screenshots/work-live-draft.webp)

</Step>
<Step>

### Save a revision

Under the editor, write **What changed?** (optional, but reviewers read it
first) and choose **Save revision N** (`⌘ Enter` or `Ctrl Enter`).

![The draft’s status line: “Live draft · based on revision 2 · Draft saved · Not saved as a revision yet”, and Dev Patel is editing](/screenshots/detail-draft-save-state.webp)

![The editor’s footer: Close editor and Save revision 3 with its keyboard shortcut](/screenshots/detail-draft-footer.webp)

Lictory waits until everything you typed is stored, then saves exactly that
as the next revision. Saving marks existing approvals outdated and asks the
same reviewers again ([approvals](/review/approvals)). The activity records
who saved the revision and who contributed.

</Step>
</Steps>

**Close editor** (or Escape) returns to the specification. The draft stays
for the next person who opens it, and is not a revision until someone saves
one.

**Discard changes…** throws away the edits no revision holds, for everyone
editing the draft, once you confirm with **Discard changes**; **Keep them**
cancels.

## Who can edit

- **The specification**: people whose discipline in the project may _edit
  specifications_, while it is not protected. Once it has been ready, it is
  [protected](/specifications#protected-specifications) and its draft closes:
  changes are proposed instead.
- **A proposed change**: its author and the collaborators they invited, while
  the change exists.

Everyone else reads the latest revision (or the change's latest saved
version), never half-typed text. If you lose the right to edit while the
editor is open, it closes with _You can no longer edit this specification
draft._

Plain work (a Task, a Bug) has no live draft: its description is edited by
one person and saved directly.

## "Draft saved" is not a revision

The draft has its own save state, separate from revisions:

| State                                     | What it means                                                                                       |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **Connecting…**                           | The editor is joining the draft.                                                                    |
| **Saving…**                               | Your latest edits are on their way to the server.                                                   |
| **Draft saved**                           | The server has stored every edit you made in the shared draft. Others see them.                     |
| **Offline — changes kept on this device** | The connection dropped. Your edits stay in this tab and are sent when it returns.                   |
| **Save failed**                           | The server refused your latest edits. They are kept in this tab; reopen the editor to keep working. |
| **Live editing unavailable**              | The editing service cannot be reached. Reading, history, discussions and reviews keep working.      |

**Draft saved** means nothing is lost, not that reviewers see it, readiness
counts it or history has it: that takes a saved revision.

## What counts as a change

A revision is created only when the specification's **title or text**
changes. Saving a draft that equals the latest revision, or whose edits
cancel out, just closes the editor. Two people saving the same draft at once
create one revision.

Every revision is **material**: it marks existing approvals outdated and
re-requests the same reviews. Changing properties (status, owner, priority,
estimate, iteration, labels) never creates a revision and never affects
approvals.

## Edit as Markdown

**Edit as Markdown** in the toolbar switches the draft to its Markdown text.
Until your Markdown edits are applied, the status line says **Markdown not
applied yet** and the text is kept on this device.

They are applied when you switch back to formatted text, save, commit or
close the editor. Parts only you changed take your text; parts only others
changed keep theirs. If someone changed the same part differently, Lictory
shows both and asks: **Keep my version**, **Keep their version**, **Keep
editing Markdown** or **Discard my Markdown edits**. Saving waits for your
choice.

## When the draft is replaced

Some changes replace a draft as a whole: a revision saved another way (by an
agent through the API, or by
[restoring](/specifications/history#restore-a-revision) an earlier one), a
merged pull request, a synced branch. Everyone editing moves to the new
content. Nothing of the old draft is mixed in silently, and nothing of yours
is dropped: edits the new content lacks are kept on your device, and the
editor offers:

- **Copy text** to paste it wherever you like;
- **Insert at end** to add it to the new draft as an ordinary edit;
- **Discard** to let it go.

The same notice appears if the editor closed before your last edits reached
the shared draft. Every replaced draft also stays stored on the server.

## What to watch for

- **Discussions are written on revisions, not drafts.** Save your edits
  before asking people to comment on them. See
  [discussions](/specifications/discussions).
- **Saving re-requests reviews.** Save when the change is ready to be
  reviewed, not after every sentence.
- **A protected specification has no live draft.** Editing it directly is
  refused; start a proposed change, which has its own live draft.
- **Offline is for short interruptions.** A dropped connection keeps your
  edits in the open tab and sends them when it returns, merged with what
  others typed. Closing the tab while offline loses unsaved edits, and the
  editor lets you type only once it has joined the draft. Wait for **Draft
  saved** before you close the page.
- **Agents do not type into live drafts.** Agents connected through MCP save
  revisions or versions of proposed changes directly, which
  [replaces the draft](#when-the-draft-is-replaced) for anyone editing it.

## Tips

- **Write together, save once.** Let the draft absorb a working session's
  back-and-forth, then save one revision with a summary of what changed and
  why.
- **Name the change in the summary.** _"Define timeout behavior for
  captures"_ tells a reviewer more than _"Updates"_, and it is the first
  thing they see in [versions](/specifications/history).
- **Close the editor when you are done.** Others then see that nobody is
  editing, and the reader marks unsaved edits so they are not forgotten.
